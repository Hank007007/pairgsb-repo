# swap-window.md — 双活窗口、校验与停旧

本文规定一把 key 从「新建」到「旧 key 停止」之间必须满足的状态、时间与校验约束。

## §1 生命周期

一个 key 在一次轮换里的阶段（phase）只有下列几值：

| 阶段 | 含义 | 供应商那边的状态 |
|---|---|---|
| `pending` | 尚未开始 | 只有旧 key |
| `created` | 新 key 已建好 | 新、旧两把同时有效 |
| `notified` | 新 key 已推给全部消费者、回执齐全 | 新、旧两把同时有效 |
| `dwell` | 双活窗口已满，可以停旧 | 新、旧两把同时有效 |
| `revoked` | 旧 key 已停 | 只有新 key |
| `rolled_back` | 本批失败并已回收 | 只有旧 key |

只有上表中相邻的迁移是合法的。`revoked` / `rolled_back` 之后不允许再回到任何更早的
阶段。没有 `pending` → `revoked` 这类跳步。

### §1.1 建新之前

新建新 key 之前，旧 key **必须仍然有效**。任何「先停旧的再建新的」顺序都是违规的，
那会产生一段没有任何可用 key 的窗口。

### §1.2 双活时长

新旧两把 key 在供应商那边必须同时有**至少 `dwell` 秒**。`dwell` 从「新 key 建好」
那一刻开始计时（不是从批次开始、也不是从推送完成开始）：消费者拿到新 key 之后，
可能有一段时间还在用旧 key，供应商必须两把都认。

停旧 key 的请求必须向供应商表达「此刻起 `dwell` 内不许真的失效」。对提供
`keep_until` 这类参数的供应商，adapter 必须把「新 key 建好时刻 + dwell」传过去；
传空串或省略表示「立即失效」，等同于没有双活窗口。对不提供该参数的供应商，
编排器仍须在本地等满 `dwell` 之后才发起停旧。

无论供应商是否支持 `keep_until`，编排器都必须本地等到双活窗口满足后再发停旧请求，
`keep_until` 是给供应商侧的额外保证，不能替代本地等待。

### §1.3 双活计时起点

「新 key 建好」指的是供应商确认创建成功的那一刻，而不是编排器本地发出创建请求的时刻。
若创建请求超时后重试，以**最终成功那次**的返回时间为准。

### §1.4 停旧的前置条件

只有同时满足下列两条，才可以停旧 key：

1. **所有**消费者都已回执成功（回执语义见 `notify.md` §2.4、§2.5）；
2. 从新 key 建好起，已经过去至少 `dwell` 秒。

两条缺一不可。任意一个消费者失败、超时或从未回执，都不得停旧。

### §1.5 停旧失败

停旧 key 的请求失败时：

- 这一批**算失败**；
- 新 key **保留**，不得为了「让批次看起来干净」而把新 key 删掉；
- 旧 key **不得强行删除**；供应商若拒绝或报错，就把这个状态如实记录下来；
- 不得把该 key 标记为 `revoked`。

### §1.6 回滚边界

批次在停旧之前失败时，回滚负责回收**本批新建**的 key，并把批次如实标记为失败。

如果批次里有的 key 已经走到 `revoked`（旧 key 已停），那么对这些 key：

- **不得**删除它们的新 key——删掉就只剩一把已失效的旧 key，这个服务将没有任何可用凭据；
- 必须把它们标记为需要人工处理，并在批次结果里明确列出；
- 批次结果不得报告为一次干净的、完整回滚。

## §2 provider adapter 契约

每个 adapter（`rotgraph/providers/`）暴露：

```python
create(spec)                     -> {"id": ..., "secret": ..., "slot": ...}
revoke(spec, key_id, keep_until=...) -> {"ok": bool, ...}
describe(spec, key_id)           -> {"state": "active" | "revoked" | "unknown", ...}
probe(spec, key_id, secret)      -> bool
```

- `create` 必须在返回里明确给出**本次新建**的那把 key。如果供应商接口一次返回多把
  （历史 key、同一账号下的其它 slot），adapter 必须按本次请求的特征（slot、创建时间、
  返回里的标记）挑出**本次新建**的那把，而不是取列表里的固定位置。
- `revoke` 的 `keep_until` 语义见 §1.2：它表达的是「这个时刻之前必须仍然有效」，
  不是「在这个时刻执行删除」。adapter 必须把它原样传给供应商。
- `describe` 供 `recovery.md` §3.3 的续跑判定使用，必须反映供应商那边的**真实**状态，
  不得读本地缓存。
- `probe` 是「用一个 secret 调一次供应商的接口、看这把 key 现在能不能用」。

## §3 校验

`rotgraph/probe.py` 的 `verify()` 负责在关键节点确认「这把 key 现在能不能用」。

- 在停旧之前，**新旧两把**都必须各被验证一次；
- 验证是向供应商发起的一次真实调用；
- 验证调用超时、连接失败、返回不可解析，一律**算失败**，不得当作通过；
- 同一个进程内，同一把 key 的验证不得复用上一次的结果；每次检查都是一次新的外部调用；
- 对不存在的 key，验证必须失败。
