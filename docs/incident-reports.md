# 线上事件记录（近两周）

> 来自对接方与合作方的工单摘录，按时间倒序。**只记录现象，未做根因分析。**

## 2026-11-09 · 合作方 B：迁移到多密钥后全部回调 401

我们在做密钥轮换：新密钥已经下发给所有发送方，但旧密钥还没有下线，
我们的发送方在切换期内混用两把密钥签名。切到你们这边之后 401 率从 0 涨到 100%，
日志里只有 `{"ok": false, "reason": "bad_signature"}`。

补充：我们发送方的 `X-Signature` 头是网关加上的，头名会被归一化成 `X-SIGNATURE`；
用 curl 手工发同一条请求（头名是小写）又能通过。

## 2026-11-07 · 合作方 A：发票 PDF 全部被拒

我们把电子发票 PDF 原文件作为回调正文发过来，签名在发送侧校验过是对的，
但你们一直返回 401 `bad_signature`。把正文换成同样的 JSON 就正常。
PDF 里有加密流，不是合法 UTF-8。

## 2026-11-05 · 内部同一秒的两条事件丢了一条

压测时 1 秒内连发 300 条不同 `event_id` 的回调，客户端收到的 202 明显少于 300，
抽查日志发现部分事件被判成 `replay`。这些事件的 `id` 各不相同。

## 2026-11-03 · 内部：重复投递偶发双执行

投递方重试机制把同一条 `event_id` 并发打了两遍（间隔约 20ms），
下游出现了两条重复的业务记录，偶尔还会在日志里看到 `sqlite3.IntegrityError`。
另外把 `DeliveryStore(":memory:")` 用在单测里时直接报 `no such table: deliveries`。

## 2026-10-31 · 安全评审：签名比较方式

外部安全评审提了一条：签名比较的实现方式在共享边缘节点上存在时序侧信道风险，
要求改成常量时间比较。评审邮件里没给具体文件，只说是"签名比对那一行"。

## 2026-10-28 · 合作方 C：对端实现始终对不上

对端（Go 实现）按我们发去的规范文档自行实现了签名，跟我们服务端算出来的值
永远不一致。双方核对过密钥、时间戳、body 都相同。
