# 密钥生命周期

一个逻辑密钥名（下称 key）属于某个租户。key 下挂着若干版本，每个版本各自持有独立的 256 位 key 材料。所有加解密都使用 AES-256-GCM。

## §2.1 版本

- 创建 key 时产生第一个版本。
- 版本号是正整数，单调递增，一经分配不复用。
- 一个 key 可以有多个可解密的版本同时存在；加密总是使用最新版本。

## §2.2 rotate

`rotate` 为指定 key 产生一个新版本，版本号在现有最大值上加一。

- rotate **只增加版本，不改变 key 名**，也不改变 key 的归属租户。
- rotate 之后，新写入的密文使用新版本；旧版本密文仍然可以解密（除非其版本已被销毁或低于 `min_decrypt_version`）。
- rotate 不得使任何已有密文变得不可解（除非同时改变了 `min_decrypt_version`，见 §2.4）。

## §2.3 min_decrypt_version

每个 key 带一个 `min_decrypt_version`，表示允许解密的最低版本。

- 默认情况下它不高于任何现存版本。
- 它可以被上调（例如轮换若干次之后淘汰过老版本）。
- 它描述的是"还能接受多老的密文"，不影响加密使用最新版本这一行为。

## §2.4 版本下限与 key_version_gone

解密时，只有 blob 头中的 key 版本 **大于等于** 该 key 当前的 `min_decrypt_version` 时才允许解密。

- 低于 `min_decrypt_version` 的密文，解密失败，对外错误码为 `key_version_gone`。
- 判断依据是 blob 头里的版本号与 key 当前状态的比较，而不是内存里是否恰好还留有该版本的 key 材料。

## §2.5 加密与版本选择

加密时写入 blob 头的版本必须是该 key 当前的最新版本。若最新版本已被销毁（不应发生，见 §2.6），加密必须失败而不是回退到旧版本。

## §2.6 destroy_version

`destroy_version` 销毁 key 的一个具体版本。

- 销毁之后，该版本的密文**一个都不能再解出来**。返回的错误码与"版本不存在"一致，不得返回明文。
- 销毁只影响被销毁的那个版本；同一 key 的其它版本不受影响，仍能正常解密。
- 销毁必须同时作用于持久化的 key 材料与进程内已经加载的缓存，不能出现"磁盘删了、内存还在"的情况。
- 销毁的版本号不得被再次分配。

## §2.7 租户隔离

- 每个 key 由其租户与 key 名共同标识。
- 同一进程服务多个租户，不同租户可以各自起同名的 key。
- 任何按名字查找 key 的路径都必须带上租户维度。只按 key 名查找会让租户 A 拿到租户 B 的 key 材料，这是不可接受的。
- 租户 A 用自己 key 加密的 blob，租户 B 即使有同名 key 也不能解开。

## §2.8 rewrap

`rewrap` 把一个已存在的 blob 重新封装到该 key 的**最新版本**上，而不接触明文语义。

- rewrap **不解原 context**：不要求调用方提供原上下文，也不因缺少上下文而失败。
- 输出的 blob 头中，key 版本为最新版本；魔数、格式版本、密钥名保持不变。nonce 属于每次加密现场生成的部分，允许重新生成。
- 原 blob 中与上下文绑定有关的信息必须原样带入新 blob，不得用调用方在本次请求里提供的 context 替换。
- rewrap 之后，用原来的 context（与 rewrap 前一致的那一份）解密，应能拿回原始明文。
- 若源 blob 的版本已不可解（低于下限或已销毁），rewrap 失败，不得产出新 blob。
