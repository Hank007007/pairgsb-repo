# cborveil manifest 的 CBOR 编码规范

本文定义设备端 OTA 代理所接受的 manifest 字节格式。文中「必须」「不得」为强制要求，
「应当」为建议。任何不满足「必须」的输入都必须使解析失败，且不得产生可用于下载的
`Target`。

## 1. 范围

一个 manifest 是一个 CBOR map，描述一次 OTA 升级：版本号、整包大小、按机型划分的
分片列表，以及厂商对整份 manifest 的 Ed25519 签名。设备收到 manifest 后依次执行：

1. 按本文第 2、3 节校验字节级合法性；
2. 按第 4、5 节映射为 manifest 结构；
3. 按第 6 节计算待签字节并验签；
4. 按第 7 节选择本机分片。

第 1 步失败时不得进入第 2 步；第 2 步失败时不得进入第 3 步。任何一步失败都必须
整体拒绝，不得返回部分解析结果。

## 2. 支持的 CBOR 子集

只接受下列 CBOR 数据项：

| major type | 含义 | 说明 |
|---|---|---|
| 0 | unsigned integer | 0 .. 2^64-1 |
| 1 | negative integer | -1 .. -2^64 |
| 2 | byte string | 任意长度 |
| 3 | text string | 必须是合法 UTF-8 |
| 4 | array | 定长 |
| 5 | map | 键必须是 text string |
| 7 | simple value | 只接受 `false`(0xf4)、`true`(0xf5)、`null`(0xf6) |

tag（major type 6）、浮点数、以及未列出的 simple value 一律不接受。manifest 中出现
不可接受的类型即为非法输入。

map 的键必须是 text string。使用 byte string 或其他类型作为键的 map 非法。

## 3. 规范化编码（canonical encoding）

manifest 必须整体采用规范化编码。规范化编码是唯一的：同一份语义的 manifest 只有
一种合法字节串。校验必须覆盖整棵数据项树，而不只是顶层。

### 3.1 map 键的顺序

在每一个 map 中（包括嵌套在 array 内、嵌套在其他 map 值内的 map），键必须按其
**编码后的完整字节串**做无符号字典序升序排列。比较对象是键的编码字节，不是键的
文本内容。相邻两个键的编码字节不得相等（即不允许重复键），后一个键必须严格大于
前一个键。

### 3.2 最短形式整数

整数必须使用能表示该值的最短头部：

- 0 .. 23 直接放在头部的附加信息中；
- 24 .. 255 使用 `0x18` + 1 字节；
- 256 .. 65535 使用 `0x19` + 2 字节；
- 65536 .. 2^32-1 使用 `0x1a` + 4 字节；
- 2^32 .. 2^64-1 使用 `0x1b` + 8 字节。

负整数同样按其参数值选择最短形式。任何可以用更短头部表示的整数编码都是非规范化
的。例如 `0x1b 00 00 00 00 00 00 00 05` 与 `0x05` 表示同一个值 5，但前者非法。
该规则适用于所有位置，包括 array 元素、map 值和嵌套结构内的整数。

### 3.3 禁止 indefinite-length

不得使用 indefinite-length 的 byte string(`0x5f`)、text string(`0x7f`)、
array(`0x9f`) 或 map(`0xbf`)。所有容器都必须带确定的长度，且内容中不得出现
break(`0xff`)。

### 3.4 唯一性

同一 map 内不得出现两个编码相同的键。结合 3.1，键的编码字节必须严格递增。

## 4. manifest 结构

manifest 的顶层必须是 map，且至少包含下列键：

| 键 | 类型 | 约束 |
|---|---|---|
| `version` | text | 非空，UTF-8 |
| `size` | unsigned integer | 整包字节数，必须大于 0 |
| `targets` | array | 至少一个元素，每个元素是第 5 节定义的 target map |
| `sig` | byte string | 长度必须为 64 |
| `key_id` | text | 非空，标识签名密钥 |

字段的互斥与必选关系：

- 上表所有键都必选，缺一即为非法。
- 同一个键在一个 map 不得出现两次（见 3.4）。
- `targets` 不得为空数组。
- `sig` 的长度必须恰好为 64 字节；长度不符的 manifest 非法。

## 5. target 结构

`targets` 的每个元素都必须是 map，包含：

| 键 | 类型 | 约束 |
|---|---|---|
| `model` | text | 非空，机型标识 |
| `url` | text | 非空，不得是空串 |
| `sha256` | byte string | 长度必须恰好为 32 字节 |
| `size` | unsigned integer | 本分片字节数，必须大于 0 |
| `offset` | unsigned integer | 本分片在整包中的起始偏移，可以为 0 |

约束：

- `url` 为空串的 target 非法；不得把空串当作「稍后填充」的占位。
- `sha256` 长度不是 32 字节的 target 非法。
- `size` 必须严格大于 0。
- `offset` 与 `size` 都必须能用有符号 64 位整数表示；超过 `2^63-1` 的值非法，
  不得回绕为负数。
- `offset + size` 必须小于或等于 manifest 顶层的 `size`（整包长度）。
- 同一个 manifest 内 `model` 不得重复。重复即整份 manifest 非法，不存在
  「后一个覆盖前一个」的语义。

## 6. 签名

待签字节定义为：把 manifest 顶层 map 中除 `sig` 和 `key_id` 之外的**所有**键值对，
按第 3 节的规范化编码重新编码后得到的字节串。

要求：

- `sig` 与 `key_id` 本身不得出现在待签字节中；它们的值不参与签名。
- 其余字段（包括未知键）都必须参与签名，且必须保留其在 manifest 中的值。
- 待签字节与 manifest 在传输时的键顺序无关：任意两份语义相同、都通过第 3 节校验
  的 manifest，必须得到逐字节相同的待签字节。
- 签名端与验签端必须使用完全相同的规则计算待签字节。
- `sig` 是用厂商 Ed25519 私钥对待签字节的签名；验签使用与 `key_id` 对应的公钥。
  验签失败即整份 manifest 非法。

## 7. 目标选择

设备以自己的机型标识调用选择逻辑。规则：

- 机型匹配必须是**完整相等**，不得使用前缀、后缀、大小写折叠或其他模糊匹配。
  设备机型为 `P1` 时，`P10`、`P1-Pro` 都不得命中。
- 一份合法的 manifest 中，与设备机型相等的 target 必须恰好有一个。
- 没有匹配项时返回「无适用分片」错误。
- 匹配项多于一个时返回「manifest 非法」错误。不得按数组顺序或 map 顺序任取一个。

## 8. 资源限制与错误处理

- 单个 manifest 的字节长度不得超过 1 MiB（1048576 字节）。超限必须在解析前拒绝。
- 数据项的嵌套深度不得超过 16 层（顶层数据项为第 1 层）。超限必须拒绝。该限制
  必须对所有分支生效，包括 map 的键与值、array 的元素。
- 解码必须消费完整输入；输入末尾存在多余字节即为非法。
- 截断的头部、长度越界的容器、非法的 UTF-8 text 都必须报错。
- 所有校验失败都必须返回错误，不得返回「尽力而为」的部分结构。

## 9. 未知键

- 未知的 text 键允许出现在 manifest 顶层与 target map 中，用于向前兼容。解析器
  必须忽略它们对已知字段的影响：未知键不得覆盖、改写或替换任何已知字段。
- 未知键仍然参与第 6 节的签名计算，且必须原样保留其值。
- 非 text 键不属于「未知键」，出现即非法（见第 2 节）。
- 不要求解析器保留未知键供上层使用；但不得因为未知键的存在而改变已知字段的解析
  结果。
