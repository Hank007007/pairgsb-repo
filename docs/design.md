# verdictmesh 设计说明

本文说明引擎的结构、数据流与设计取舍。可观察行为以 [`policy-semantics.md`](./policy-semantics.md) 为准；本文不重复逐条规范，只解释为什么这样组织。

## 1. 定位

verdictmesh 是一个**内嵌**的策略决策点（PDP）。它不监听端口、不连接外部服务，只作为库被业务进程引用：

```js
import { createEngine } from 'verdictmesh';

const engine = await createEngine({ policyDir: './policies' });
const verdict = engine.decide({
  principal: '/users/alice',
  resource: '/docs/reports/q3',
  action: 'read',
  context: { role: 'member' },
});
// => { allow: boolean, matchedPolicy: string | null, reason: string }
```

之所以做成内嵌库而不是独立服务：决策延迟要落在进程内、策略变更频率远低于请求频率、接入方希望自己在启动阶段完成策略校验并快速失败。

## 2. 模块划分

```
src/
  index.js        对外入口：createEngine 与再出
  engine.js       决策主流程、请求校验、资源候选展开
  rules.js        规则规范化与格式校验
  policy-store.js 读取策略目录、解析、汇总
  glob.js         路径模式编译与匹配
  conditions.js   条件求值
  batch.js        批量决策
  cache.js        带 TTL 的结果缓存
```

分层意图：

- **加载期**（`policy-store` → `rules`，以及 `PolicyEngine` 构造时的模式编译）：一次性完成 JSON 解析、字段校验、模式编译。失败即抛 `PolicyFormatError`，让接入方在进程启动时发现。
- **运行期**（`engine` → `glob` / `conditions` / `batch` / `cache`）：请求进来后只做匹配与求值，不再触碰磁盘，也不再重新解析。

`PolicyEngine` 构造时接受显式 `rules` 数组，因此单测和上层封装可以绕过文件系统；`createEngine` 是"读目录再构造"的便捷包装。

## 3. 决策流水线

一次 `decide` 的逻辑顺序：

1. **请求校验**：`principal` / `resource` / `action` 必须是非空字符串，`context` 必须是对象或省略。校验失败抛 `TypeError`。
2. **候选资源展开**：把请求资源按 `/` 从细到粗展开成候选序列。
3. **逐规则匹配**：对每条规则依次检查主体、资源（对候选序列）、动作、条件。
4. **汇总**：收集全部命中规则的 `effect`，按规范里的冲突消解规则得出最终结果。

把"匹配"与"汇总"分成两个概念很重要：匹配是每条规则独立判断的事实，汇总才引入 `deny` 与 `permit` 的优先级。这样规则声明顺序只在 `matchedPolicy` 的选取上起作用。

## 4. 匹配与冲突消解是两个问题

"规则是否命中"是每条规则可以独立回答的事实；"最终放行还是拒绝"则要在全部命中规则上做冲突消解，`deny` 恒定优先。把这两件事区分开，可以让规则的声明顺序只影响 `matchedPolicy` 的选取，而不影响 `allow`——接入方调整策略文件的排列时，不应观察到放行结果发生化。

规则集通常只有几十到几百条，逐条匹配的代价远小于一次业务请求本身的耗时。若将来需要优化，可以按 `principal` 前缀分桶，但分桶只改变检索方式，不改变上述语义。

## 5. 模式编译

路径模式在构造引擎时编译一次并缓存。使用编译产物而不是在每次请求时重新解析，有两个原因：一是避免重复工作，二是让格式错误尽早暴露。

模式匹配必须是**整串锚定**的，且只对 `/`、`*` 有特殊语义，其余字符按字面量处理。接入方的资源名里出现 `.`、`+`、`(foo)` 是常见情况（如版本号、URL 片段），不应被当作正则元字符。

## 6. 条件求值

条件求值是一个纯函数：输入 `(condition, context)`，输出布尔值。它不抛异常、不读外部状态。这带来两个直接好处：

- 缺失键可以表达为"该规则不命中"，而不是让异常穿过引擎边界变成 5xx。
- 条件可以独立单测，不必构造完整引擎。

比较运算集中在一个小的运算符表里，新增运算符只改一处。类型处理遵循规范：数值优先按数值比，不可比时该运算符为假。

## 7. 批量与缓存

`decideMany` 是 `decide` 的位置保持包装：结果数组与请求数组一一对应，第 `i` 项必须等于单独调用第 `i` 个请求的结果。这条不变量优先于任何缓存收益——缓存若与逐条调用产生差异，缓存就是错的。

缓存的定位是**可关闭的优化**：

- 键必须覆盖所有参与决策的输入；
- 值与结果结构隔离（返回副本），避免调用方修改缓存内容；
- 有过期时间与容量上限，避免无界增长；
- `cache: false` 时完全退化为逐条计算。

## 8. 错误分类

| 场景 | 错误类型 | 时机 |
|---|---|---|
| 策略文件语法/字段错误 | `PolicyFormatError` | 加载期 |
| 请求字段缺失或类型错误 | `TypeError` | 运行期 |
| 条件引用的键不存在 | 不抛错，规则不命中 | 运行期 |

加载期与运期错误分开，接入方可以据此决定"启动失败"还是"按 4xx/5xx 返回"。

## 9. 目录约定

```
policies/*.json   生产样例策略，按文件名排序后依次加载
test/             node:test 测试，node --test 直接运行
examples/         可执行的接入示例
docs/             语义规范与设计说明
```

策略目录里的每个 `.json` 可以是一个规则数组，也可以是 `{ "rules": [...] }`。跨文件的 `id` 必须唯一，重复视为格式错误，以免 `matchedPolicy` 产生歧义。

## 10. 非目标

- 不做策略的动态热更新（重启或重新构造引擎即可）。
- 不做角色继承、属性源拉取、审计落库；这些由接入方在其上层完成。
- 不提供 HTTP 接口。
- 不引入任何第三方依赖，仅使用 `node:` 内置模块。
