# notify.md — 推送给消费者与回执

新 key 建好之后，编排器通过内部 webhook 把它推给批次里的每一个消费者服务，并等待回执。

## §1 推送内容

- body 是 JSON，包含 `service`、`slot`、`key_ref`、`key`（新 key 明文，仅出现在发往
  消费者的请求里）、`batch` 等字段。
- 请求方法为 `POST`，`Content-Type: application/json`。
- 请求体一经序列化成字节就不再改动——签名所覆盖的字节与实际发出的 body 必须是同一串。

## §2 认证

### §2.1 请求头

每个 webhook 请求必须带：

| 头 | 含义 |
|---|---|
| `X-Rot-Timestamp` | 发出时刻，Unix 秒（十进制字符串） |
| `X-Rot-Nonce` | 每次请求唯一的随机串 |
| `X-Rot-Signature` | 见 §2.2 |

三者缺一不可。接收方只看这三个头加 body，不认任何其它字段。

### §2.2 签名算法

签名原文是下列三段的拼接，段间用单个 `|` 分隔：

```
timestamp + "|" + nonce + "|" + body
```

用消费者条目里的 `secret` 做 HMAC-SHA256，输出小写十六进制字符串。

签名原文包含 timestamp 与 nonce，**不是**只签 body。只签 body 的签名在接收方那里
无法抵御重放，也无法被绑到某个具体时刻与某次具体请求上。

### §2.3 时间戳

接收方把 `X-Rot-Timestamp` 与自己当前时间比较，绝对偏差**超过 300 秒**即判失败，
无论签名是否正确。因此编排器必须如实填写当前时间，不得复用旧请求的 timestamp；
`X-Rot-Signature` 必须是对**本次** timestamp 与 nonce 签出来的。

### §2.4 重试与回执语义

- 接收方返回 **2xx**：该消费者回执成功。
- 接收方返回 **4xx**：属于请求本身的问题（签名错、时间戳过期、body 不合法等），
  重试不会变好。**只发一次，不重试**，该消费者记为失败。
- 接收方返回 **5xx**连接错误、读超时：可重试。按**指数退避**重试，次数与退避由
  `rotation-plan.md` §2.9 的 `notify` 配置给出（缺省首发 + 4 次重试，退避从 1 秒
  起、每次翻倍、上限 8 秒）。次数用尽仍无 2xx，该消费者记为「没有回执」。
- 其它状态码（3xx 等）按失败处理，不重试。

每次重试都是一次新请求：新的 timestamp、新的 nonce、对应当前 body 的新签名。

### §2.5 回执的完整性

`await_acks()` 的返回值必须让调用方**无条件**判断出「是不是全部成功」。约定：

- 返回值里逐个消费者给出是否成功，并且必须显式列出尚未回执 / 回执失败的消费者名字；
- 必须能区分「全部成功」与「部分成功」「一个都没收到」三种情况；
- 不存在「返回值非空就代表齐了」这种读法。

调用方（`runner.advance()`）不得只看返回值是否为空，而必须按上述约定判定。

## §3 推送给谁、什么顺序

- 批次里的每一个消费者都要收到**每一个** key 的新值：消费者侧按 `service`/`slot`
  索引自己需要的凭据，编排器不做按依赖关系的裁剪。
- 推送与回执按 `rotation-plan.md` §3 决定好的 key 顺序进行：一个 key 的推送与回执
  全部结束之后，处理顺序里的下一个 key。这样下游消费者在拿到上游 key 之前不会先
  拿到自己的新值。
- 某个消费者对某个 key 最终失败（4xx 或重试用尽）时，该 key 不得进入双活阶段，
  见 `swap-window.md` §1.4。
