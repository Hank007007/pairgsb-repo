# 对端鉴权设计口径

本文是本仓库的规范性文档。文中「必须」「不得」「应当」都是硬性约束；实现与本文冲突时以本文为准。

术语：

- **本服务信任域**：`policies/trust.json` 中 `trust_domain` 的值，例如 `corp`。
- **服务身份**：从对端证书中提取出的 `<service>` 段，例如 `payments`。
- **调用表**：`policies/*.json` 中描述「哪个服务身份可以调用哪些方法」的规则集合。
- **信任束（bundle）**：`internal/bundle/` 下按 epoch 组织的信任锚与中间 CA。

---

## §1 握手与信任链

1.1 服务端必须以双向 TLS 提供服务：既验证自己的服务端证书，也验证对端出示的客户端证书。

1.2 对端证书的验证必须完整走一遍证书链验证，而不是只确认「对端出示了证书」。对端证书必须：

- 由信任束中某个已登记的中间 CA 签发，且该中间 CA 本身可回溯到信任束中的某个信任锚；或
- 由信束中的某个信任锚直接签发。

1.3 信任束按 epoch 组织，轮换期间可能同时存在多个 epoch。证书链只在其签发 epoch 对应的锚集合内验证；已退役 epoch 下的证书不得再被接受。新 epoch 启用后，对端应当能够用新锚签发的证书完成握手。

1.4 以下证书必须在 TLS 握手阶段失败，不得进入 RPC 层：

- 自签证书；
- 链不完整、无法回溯到信任锚的证书；
- 由未登记 CA 签发的证书；
- 已过期、未生效、用途不含客户端认证的证书。

1.5 握手失败必须以 TLS alert 终止。握手阶段的错误信息不得携带策略层细节。

1.6 客户端对服务端证书的验证由客户端负责，不属于本库的职责范围。

---

## §2 身份提取

2.1 对端身份**只**来自证书里的 URI SAN，格式固定为：

```
spiffe://<trust-domain>/<service>/<instance>
```

其中 `<instance>` 可以省略，省略时 URI 为 `spiffe://<trust-domain>/<service>`。

2.2 一个 URI SAN 要被认作有效身份，必须同时满足：

- scheme 为 `spiffe`；
- authority（host）与本服务信任域相等，按 URI 的 host 规则比较；
- path 由一段或两段组成：`<service>`，或 `<service>/<instance>`；
- 各段非空，且不包含空段、`.`、`..` 或额外的 `/`。

2.3 库对外暴的服务身份是 `<service>`。`<instance>` 只用于审计与日志，不参与授权判定；同一服务的不同实例共享同一服务身份。

2.4 证书中出现多个 URI SAN 时，只有当所有 URI SAN 都指向同一个服务身份时才可以接受；只要存在指向其它信任域、其它服务或格式非法的 URI SAN，就必须整体拒绝。不得只取第一个 URI SAN 作为身份。

2.5 证书中没有任何 URI SAN 时必须拒绝。不得回退到 DNS SAN、Common Name、邮箱或任何其它字段来推断身份。特别是：只带 `DNS:payments` 的证书不能被认作 `payments`。

2.6 信任域不符（例如 `spiffe://evil.example/payments`）、scheme 不符、路径段数不对、段为空，均视为「无可识别身份」。库必须返回明确的错误，且不得把对端可控的字符串拼进错误信息以外的地方。

2.7 身份提取失败时，该 RPC 必须被拒绝；调用方不得看到任何策略匹配细节。

## §3 策略匹配

3.1 调用表规则作用于 §2 提取出的服务身份。

3.2 `from` 字段按 `/` 分段后**逐段整段相等**比较。它不是前缀匹配，不是子串匹配，也不是 glob 通配。例如规则 `from: "payments"` 只匹配服务身份 `payments`，不匹配 `payments-backup`、`payments2`、`payments/internal` 或 `paymentsx`。

3.3 `from` 中可以使用 `*`，但 `*` 只顶**一个**分段，且该段必须非空：

- `from: "*"` 匹配任意单段身份（如 `payments`、`ledger`），不匹配多段身份（如 `payments/v2`）；
- `from: "payments/*"` 匹配 `payments/v2`，不匹配 `payments` 本身，也不匹配 `payments/v2/eu`；
- `from: "*"` **不得**匹配空身份或格式非法的身份。

3.4 身份为空字符串、无法解析、或未通过 §2 校验时，任何规则都不得匹配，包括 `from: "*"`。

3.5 `to` 字段匹配被调用的方法名（如 `/ledger.v1.Ledger/Debit`），同样按 `/` 分段整段相等；`*` 只顶一个分段。

3.6 规则集合中没有任何规则匹配时，默认拒绝。

3.7 匹配判定必须是确定性的：同一对端、同一方法，无论规则在文件中以什么顺序出现、无论运行时容器以什么顺序遍历，结果都必须相同。

---

## §4 deny 优先级

4.1 调用表可以同时包含 permit 与 deny 两类规则。deny 的优先级高于 permit。

4.2 同一对端、同一方法同时命中至少一条 permit 与至少一条 deny 时，结果必须是**拒绝**。

4.3 求值不得在遇到第一条 permit 时短路返回允许。必须对整个规则集合做完求值，先判断是否存在命中的 deny，再考虑 permit。

4.4 deny 优先与匹配的具体程度无关：更「精确」的 permit 不能覆盖任意一条 deny。

4.5 deny 优先与规则加载顺序、规则容器遍历顺序、并发度均无关。同一输入重复求值任意多次，结果必须一致。

4.6 判定结果只允许是「允许」或「拒绝」两种；拒绝时不得回退为允许。

---

## §5 调用面覆盖

5.1 库同时服务 unary 调用与 streaming 调用。两种调用形态必须经过同一套 §3、§4 的授权判定。

5.2 streaming 调用的授权在流建立时执行。被拒绝的对端不得建立流，也不得在流建立后补做判定。

5.3 不存在「TLS 通过即可调用」的路径。任何 RPC 入口都必须先得到服务身份，再得到授权结论。

5.4 unary 与 streaming 对同一对端、同一方法必须给出一致的授权结论。

---

## §6 错误与日志

6.1 授权拒绝对外表现为统一的错误码，是否附带原因由部署方决定；不得附带命中的规则内容。

6.2 审计日志可以记录服务身份、实例、方法与授权结论，但不得记录对端证书原文。

6.3 身份提取错误与授权拒绝在审计上应可区分，但两者对调用方都表现为拒绝。
