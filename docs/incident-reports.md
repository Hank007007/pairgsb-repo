# Incident report — INC-2417

**状态**：已结案
**影响面**：一个租户下的只读对象存储前缀
**时间线**：全部时间为 UTC

## 摘要

2024 年 9 月，一名外包分析人员拿到了一份标注为 10 分钟有效的只读凭据。凭据在标注的作废时刻之后仍能继续使用，并读到了同租户下另一个前缀中的对象。凭据没有转交给第三方；复盘关注的是校验环节实际做出的判断与文档口径之间的偏差。

## 时间线

| 时间 | 事件 |
|---|---|
| 09-03 14:02 | 分析人员通过 `POST /grants` 申请 `read`，路径为其项目前缀，`ttlMs` 为 600000 |
| 09-03 14:02 | 服务返回凭据，签发记录显示 `expiresAtMs` 为 14:12 |
| 09-03 14:12 | 凭据标注的作废时刻到达 |
| 09-03 15:40 | 分析人员的脚本以同一凭据成功取到对象 |
| 09-04 09:15 | 同一凭据被用于访问相邻前缀，返回 200 |
| 09-04 11:30 | 值班同学在访问日志里发现异常前缀，手工封禁客户端并回该凭据 |
| 09-05 10:00 | 复盘开始 |

## 观察到的现象

1. 过期之后的请求仍然通过校验。访问日志里能看到请求时间已晚于凭据的 `expiresAtMs`，响应是 200。
2. 相邻前缀与本项目前缀共享前若干字符，校验把二者当成同一个前缀。
3. 凭据里写的是 `read`，访问日志里出现了一个以 `read` 为子串的更宽的动作名，同样返回 200。
4. 值班同学通过撤回入口回收过一次凭据，后续请求没有被拦住。
5. 复核签发记录时发现，同一时刻为同一租户连续签发的两条凭据拿到了同一个标识。

## 复盘结论

- 过期判定没有以凭据自带的作废时刻为准；判定边界与文档描述不一致。
- 路径比较按字符串前缀进行，租户根之后多一个字符的兄弟前缀被判为「在根下」；路径中带有上跳片段或百分号编码时也没有先换算成同一形态。
- 动作比较在精确匹配之外还接受了一次宽松匹配，动作名是授权动作超串时被放行。
- 撤回状态只存在于签发进程的内存中，校验路径没有读取它，进程重启后状态丢失。
- 标识生成没有与签发时刻绑定，同一毫秒内的两次签发发生碰撞，导致一次撤回影响多条凭据。

## 影响

- 单条凭据在其标注有效期之后仍可读取，最长持续约 45 小时。
- 越权读取的范围限制在同一租户的相邻前缀内，未跨租户。
- 撤回操作在事故处置期间没有起到预期作用。

## 待跟进（流程侧）

- 与受影响租户完成沟通，更新对外说明中关于撤回生效时间的表述。
- 在访问日志中补充凭据标识与签发时刻，便于后续按凭据维度检索。
- 把「签发与校验两侧的路径形态必须一致」写进接口评审清单。
