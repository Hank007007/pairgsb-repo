# decframe 帧格式规范

本文档定义边缘节点与接入网关之间传输的二进制帧格式，以及网关侧解码器必须维持的约束。文中「必须」「不得」为强制要求。

## 1. 术语

- **帧缓冲区**：调用方交给解码器的一段完整字节序列，对应一个待解帧。
- **游标**：解码器在帧缓冲区中的读取位置。
- **值**：帧体内部的类型化数据单元，见第 3 节。
- **容器**：数组或 map，可以包含其他值。

## 2. 帧结构

一帧由帧头和帧体组成，二者首尾相接，中间不得有空隙。

```
+--------+---------+------------------+------------------+
| magic  | version | body length      | body             |
| 4 字节 | 1 字节  | LEB128 变长整数  | body length 字节 |
+--------+---------+------------------+------------------+
```

### 2.1 魔数

固定为 ASCII `DFRM`（字节 `0x44 0x46 0x52 0x4D`）。不匹配即视为非法帧。

### 2.2 版本

固定为 `0x01`。其他本值一律拒绝。

### 2.3 帧体长度

- 使用无符号 LEB128 编码的无符号 32 位整数。
- 最多占 5 个字节。
- 第 5 个字节只能使用低 4 位；任何更高位、第 6 个及以后的字节、或超过 32 位表示范围的编码都是非法编码。
- 长度值必须大于等于 0 且不超过 16 MiB（16777216 字节）。
- 该长度只描述帧体，不包含帧头。

### 2.4 帧体

帧体恰好包含一个值，且该值必须为 map。该 map 的键为字符串，用于承载业务字段。

## 3. 值的编码

每个值以一个字节的类型标签开始，其后紧跟该类型的负载。

| 标签 | 类型 | 负载 |
|---|---|---|
| `0x01` | string | LEB128 u32 字节长度 + 该长度的 UTF-8 字节 |
| `0x02` | bytes | LEB128 u32 字节长度 + 该长度的原始字节 |
| `0x03` | array | LEB128 u32 元素个数 + 依次排列的若干值 |
| `0x04` | map | LEB128 u32 键值对个数 + 依次排列的若干「键值对」 |

约定：

- array 元素和 map 的键、值都必须是第 3 节定义的完整值。
- map 的键的类型必须是 string。
- 任何未在表中列出的标签都是非法标签。
- 所有 string 值（包括 map 的键）必须是合法 UTF-8。
- 一个 map 中，任意两个键的字节内容不得相同。这里的「相同」按字符串内容比较，不涉及规范化。

## 4. 帧字段

帧体 map 中以下键具有约定含义：

| 键 | 类型 | 是否必需 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 消息标识 |
| `kind` | string | 是 | 业务类别 |
| `meta` | map（键、值均为 string） | 否 | 元数据；缺省视为空 map |
| `payload` | bytes | 否 | 业务负载；缺省视为 nil |

- 若 `id` 或 `kind` 缺失，或类型不符，整帧非法。
- `meta` 出现但类型不是 map，或其键、值不是 string，整帧非法。
- `payload` 出现但类型不是 bytes，整帧非法。
- 本版本未定义的键予以忽略，但其值仍须满足第 3 节的类型与合法性约束，且参与元素计数。
- 解码结果中 `Payload` 指向帧缓冲区内部，调用方不得在解码器返回后修改帧缓冲区。

## 5. 畸形帧与错误码

下表的每一行都是强制行为。错误码是解码器导出的哨兵错误，调用方可以通过 `errors.Is` 判断。除下表列出的错误外，解码器还可以因帧头不完整、未知类型标签、必需字段缺失或类型不符而返回相应错误；但不得返回与下表中更具体的错误相冲突的错误码。

| # | 畸形帧 | 错误码 |
|---|---|---|
| 1 | 长度或计数位置的 LEB128 编码超长带溢出位或超过 u32 范围 | `ErrVarintOverflow` |
| 2 | 任何值声明的长度大于帧缓冲区剩余字节数 | `ErrLengthExceedsBuffer` |
| 3 | 帧体长度超过 16 MiB | `ErrFrameTooLarge` |
| 4 | 容器嵌套深度超过 8 层 | `ErrDepthExceeded` |
| 5 | 同一个 map 内出现重复键 | `ErrDuplicateKey` |
| 6 | map 的键不是合法 UTF-8（以及其他 string 值不是合法 UTF-8） | `ErrInvalidUTF8` |
| 7 | 一个帧解码完成后，帧缓冲区仍有未消费的字节 | `ErrTrailingBytes` |
| 8 | 一帧内解码出的值总数超过 4096 | `ErrTooManyElements` |

补充约定：

- 错误判定顺序：先检查魔数、版本，再检查帧体长度是否超过 16 MiB，然后解码帧体；帧体内部的错误按解码遇到顺序返回，最后检查尾部字节。
- 任何畸形输入都必须返回错误，不得 panic，不得越界读写。
- 解码器不得根据帧内声明的长度或元素个数直接申请等量内存；所有内存占用必须受实际收到的字节数约束。
- 「元素总数」指一帧内被解码出的值的个数：帧体根值计 1，容器中的每个直接子值（map 的键与值分别计算）各计 1。该计数在整帧范围内累计，不因容器层级而重置。

## 6. 资源上限

| 项目 | 上限 |
|---|---|
| 帧体字节数 | 16 MiB |
| 容器嵌套深度 | 8 层（帧体根 map 为第 1 层） |
| 单帧元素总数 | 4096 |

深度达到上限的容器仍可拥有标量子值；只有再向内嵌套容器才会触发 `ErrDepthExceeded`。

## 7. 合法帧示例

以下十六进制表示一个合法帧（空格仅用于阅读）：

```
44 46 52 4d 01 34
04 04
  01 02 69 64        string "id"
  01 04 6e 6f 64 65  string "node"
  01 04 6b 69 6e 64  string "kind"
  01 04 70 69 6e 67  string "ping"
  01 04 6d 65 74 61  string "meta"
  04 01
    01 01 6b        string "k"
    01 01 76        string "v"
  01 07 70 61 79 6c 6f 61 64  string "payload"
  02 03 61 62 63     bytes "abc"
```

解码结果：

```
Frame{
    ID:      "node",
    Kind:    "ping",
    Meta:    map[string]string{"k": "v"},
    Payload: []byte("abc"),
}
```

帧体长度为 `0x34`（52 字节），与帧体实际字节数一致，帧缓冲区在帧体结束后立即结束。
