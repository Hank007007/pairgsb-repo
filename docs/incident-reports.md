# frameseal 网关事故记录

本文件记录与帧解码相关的线上事故，供后续设计与回归参考。协议口径以 `docs/frame-rules.md` 为准。

## INC-2024-03-11 — 分片消息导致网关 OOM 重启

**现象**

- 14:07 起网关单实例 RSS 从约 380 MiB 持续爬升，14:19 达到容器内存上限，进程被 OOM killer 终止，重启期间该实例上的连接全部断开。
- 重启前后日志里能看到的只有 `message:assembled` 一条，`size=322122547`（约 307 MiB），以及一条来自同一连接的 `frame:decoded` 序列，`opcode=0` 与 `opcode=1` 交替，共数十万帧。
- 该连接的对端是一个客户端 SDK 的早期版本，它在发送大对象时不分批，而是把一个 300 MB 的二进制对象切成大量很小的分片连续发送。

**初步分析**

- 网关侧没有对分片消息的长度和帧数设任何累计上限，重组器来一帧拼一帧，拼接结果跟着对端发的字节数线性增长。
- 拼接用的是「每次复制已有内容再追加」的方式，峰值内存约为消息本身的两倍以上。
- 帧数也没有上限，即使每帧 payload 很小，帧对象本身与每帧的 Buffer 切片仍然占用内存。

**后续要求**

- 分片消息的总 payload 长度与总帧数都必须有硬上限，累计在重组器内部完成，超限立即中止，不再缓存后续分片。具体数值见 `docs/frame-rules.md` §4.7 与 §9。
- 上限判断要在追加之前完成，而不是先拼起来再量长度。
- 单帧长度也必须有上限，不能只依赖对端「应该不会发这么大」的假设。

## INC-2024-06-02 — 日志里的乱码与 `%00`

**现象**

- 审计日志与业务库里出现了一段本应为中文 JSON 的文本，内容变成大量 `�` 以及若干被 `%00` 截断的字段。
- 同一批请求里，客户端 SDK 的发送端日志显示原文正常；抓包里的 WS 帧与客户端发出的字节一致，说明数据在网关侧被改变。
- 受影响的消息都来自协商过 permessage-deflate 的连接。另有一部分消息来自同一连接，但客户端声明这些消息没有压缩。

**初步分析**

- 网关在连接协商过压缩之后，对所有消息一律按 deflate 解压，没有看该消息起始帧的 RSV1 是否置位。未压缩的消息被当作压缩流喂给解压器后，解压器在错误的位置结束，解出的字节与原文无关。
- 文本校验用的是宽松解码，非法序列被替换成 U+FFFD 后仍被当作合法文本交付，最终写进日志和数据库。
- payload 中的 `0x00` 没有被拦，落到数据库字符串列时被截断，日志里表现为 `%00`。

**后续要求**

- 是否解压只看消息起始帧的 RSV1，不看连接是否协商过压缩。见 `docs/frame-rules.md` §8.2。
- 解压必须校验压缩流在 `0x00 0x00 0xFF 0xFF` 尾巴处恰好结束，截断或多出字节都要拒绝，见 §8.5。
- 文本消息必须做严格 UTF-8 校验并拒绝 NUL，见 §7.2 与 §7.3。

## INC-2024-09-18 — 审计重放对不上

**现象**

- 审计侧对同一批连接做重放校验时，约有 0.3% 的帧无法与抓包字节对上，差异恰好是 payload 的前若干字节被改变。
- 差异只出现在带 mask 的客户端帧上，且改动的字节数与 4 字节 masking key 相关。

**初步分析**

- 网关解 mask 时直接改写了收到的缓冲区，审计侧拿到的已经是解码后的数据；抓包比对时自然对不上。
- 同一块缓冲区被多处共享（帧对象、审计队列、重放缓存），任何一处解码都会影响其他读者。

**后续要求**

- 解 mask 必须产生新的 payload 缓冲区，调用方传入的字节保持在线上的原样。见 `docs/frame-rules.md` §2.3。
- 审计、重放与抓包比对读取的必须是原始字节。

## INC-2025-01-07 — 客户端声明了超大帧

**现象**

- 某客户端发来一个长度码为 127 的帧，扩展长度字段为 `0x0000000100000000`（4 GiB）。网关解析出的 payload 长度是一个很小的数（与低 32 位有关），随后按这个小长度切出 payload，帧边界整体错位，后续字节被当作新帧头解析，连接进入持续的协议错误状态并反复重连。
- 另一批请求里出现扩展长度最高位为 1 的值，网关同样没有拒绝，解析出的长度为负数或极大值，行为不可预期。

**初步分析**

- 64 位扩展长度只读了低 32 位，高 32 位被丢弃。
- 长度码 127 的扩展长度没有检查最高位。
- 单帧长度没有上限，即使读出了真实长度也不会被拒绝。

**后续要求**

- 64 位扩展长度必须整体读入；高 32 位非零或最高位为 1 直接按协议错误处理。见 `docs/frame-rules.md` §1.2 与 §1.3。
- 单帧 payload 上限见 §1.5。
