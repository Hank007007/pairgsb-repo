# hopfence 设计说明

hopfence 是内网南北向的转发代理。外部请求进入后，按路径前缀路由到配置中固定的上游，转发前做头部处理与路由 ACL 判断，转发后写一条访问日志。

本文说明设计取舍与信任边界，只描述「正确行为应该是什么」，不给出实现。规范性条款见 `docs/forwarding.md`，配置项见 `docs/routes.md`。

## 1. 组件与处理顺序

| 组件 | 职责 |
|---|---|
| 配置加载 | 读取并校验 JSON 配置；上游与路由只来自配置 |
| 请求入口 | 接收 HTTP 请求，串起各处理步骤 |
| 路径处理 | 解码百分号转义，并相对所选前缀清理路径 |
| 路由选择 | 按最长前缀选择唯一路由 |
| 路由 ACL | 按来源地址与排除路径决定放行与否 |
| 头部处理 | 剥离逐跳头、重写客户端地址相关头 |
| 转发 | 把请求送到上游，把响应回写客户端 |
| 访问日志 | 每个请求恰好一行，字段可稳定切分 |

处理顺序固定：确定客户端地址 → 解码路径 → 选路 → 清理路径并执行 ACL → 构造转发头 → 转发 → 写日志。顺序本身是设计的一部分，因为每一步的输入都来自上一步的结论。

## 2. 信任边界

- **上游与路由来自配置。** 客户端无法新增、删除或改变任何一条路由，也无法把请求导向配置之外的上游。路由表在启动时编译完成，运行期只读。
- **客户端地址来自 TCP 连接。** 请求头里的任何转发链信息都是客户端可控输入，不能作为身份依据，也不能被当作「上一跳已经验证过」的证据。
- **路径来自客户端，必须先解码再用于任何安全判断。** 路由选择、ACL 排除、转发、日志必须基于同一份结论，避免「判定用一套、转发用另一套」。
- **日志字段来自客户端，必须转义。** 日志行的结构不能由客户端内容决定，否则一条请求可以伪造多条记录。

## 3. 关键决策

### 3.1 客户端地址

客户端地址只有一个来源：TCP 对端。入站 `X-Forwarded-For` 整体丢弃，不取其中任何一段，也不拼接进新值。发往上游的请求只带一条由本跳写入的 `X-Forwarded-For`，值为对端 IP 字面量；`X-Real-IP` 同样由本跳覆盖。日志中的地址与这条头保持一致，否则排障时两个来源会互相矛盾。

对端地址无法解析为 IP 时无法做出可靠判定，请求不转发，返回 `500`。

### 3.2 路径

编码形态（`%2e`、`%2f`、`%252e` 等）可以绕开按字符串前缀做的判断，因此路由与 ACL 一律在解码后的路径上进行，且只解码一次。

清理按段进行，目的是让同一路径在选路、ACL、转发、日志中只有一种解释。选路在解码之后、`..` 回退之前完成；`..` 不能让路径逃出所选路由前缀：一旦需要退到前缀之上，请求就被该路由拒绝，而不是改投别的路由——否则前缀路由就不再是隔离边界。清理结果由代理内部消化，不向客户端发重定向。

### 3.3 转发头

逐跳头描述的是「这一跳」的连接语义，跨过代理就失效，因此不得转发，也不得回写。`Connection` 中点名的扩展头同理，并且头名比较不区分大小写、忽略首尾空白。端到端头（业务头、`Authorization`、`Content-Type` 等）原样转发。

客户端身份头是例外：它们由本跳重写，入站值不透传。

### 3.4 访问日志

日志是运维与审计的输入，格式必须稳定：固定字段、固定顺序、单空格分隔、每请求一行。字段内容来自客户端，因此任何空格、控制字符、`"`、`%`、`\` 都要按 §7 的百分号规则转义到「不变行结构与字段切分」的程度。转义只影响书写形式，不改变字段表达的信息。

## 4. 错误处理

错误响应的状态码见 `docs/forwarding.md` §8。错误响应体不回显客户端可控内容，避免把请求路径或头原样反射回去。上游失败与本地判定失败必须可区分：本地拒绝用 `4xx`，上游不可达用 `502`。

## 5. 明确不做的部分

- 不解析请求体，不做内容改写。
- 不做 TLS 终止、限流、缓存、重试。
- 不在运行期重载配置。
- 不信任任何客户端提供的转发链或身份头。
