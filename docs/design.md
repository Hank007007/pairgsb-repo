# headlace 设计说明

## 1. 定位

headlace 位于通知平台与 `net/smtp` 之间，负责把业务层的数据模型转成一份完整的 MIME 报文。业务层不接触任何邮件语法：它只提供结构化字段，headlace 决定这些字段如何落进头部和正文。

```
业务层 ──> smtp.Compose(msg Message) ──> []byte ──> net/smtp.SendMail
                    │
      ┌─────────────┼──────────────┬───────────────┐
      │             │              │               │
   header        addr            mime            （校验）
  编码/折行     列表/显示名     boundary/正文
```

## 2. 模块职责

| 包 | 职责 |
|---|---|
| `internal/header` | 头值编码（RFC 2047）、折行、头块渲染 |
| `internal/addr` | 地址列表切分、显示名与地址规格的格式化 |
| `internal/mime` | boundary 分配、正文组装、附件 Content-Disposition |
| `internal/smtp` | `Message` 模型与 `Compose` 入口，串联上述模块并做最终校验 |

各包之间只通过显式的字符串/结构体交互，不共享可变状态。

## 3. 数据模型

`Message` 由上游填充，字段语义如下：

- `From`：发件人，单个地址，可以带显示名。
- `To`：收件人列表，逗号分隔的人类可读字符串。
- `ReplyTo`：可选，回复地址列表，语义与 `To` 相同。
- `ListUnsubscribe`：可选，退订入口，按 RFC 2369 的 `<...>` 形式给出。
- `Subject`：任意 UTF-8 文本。
- `Text` / `HTML`：正文，UTF-8，可含空行。
- `Attachments`：文件名与内容。

`Message` 的所有字段都视为不可信输入。

## 4. 正确行为概要

规范细节见 `docs/mail-headers.md`。这里只描述设计意图：

### 4.1 防御边界

所有外部字符串在进入头块前必须经过同一条流水线：

1. **语法校验**：头名匹配允许集合；头值不含裸 CR/LF 与控制字符。失败即返回错误，不做「清理后继续」。
2. **编码**：非 ASCII 与控制字符按 RFC 2047 编码，单个 encoded-word 有长度上限。
3. **折行**：在合法切点折叠，保证行长上限和 UTF-8 字符完整性。
4. **反解自检**：地址用 `net/mail` 反解，主题/显示名解码后与原文比对。

这四步的顺序是有意为之：先拒绝，再编码，再排版，最后验证排版没有破坏语义。任何一步失败都应中止整个 `Compose`，而不是产出部分报文。

### 4.2 地址

地址列表的切分要理解引号与注释的嵌套结构，不能按字符扫描。输出时只保留「显示名 + 地址」，注释属于传输中的排版信息，不进入最终报文。显示名在必要时加引号并转义。

### 4.3 MIME 结构

正文与附件的关系应当让通用邮件客户端能正确展开：纯文本与 HTML 是同一封邮件的两种呈现，附件是独立的部分。boundary 必须随机且不与正文冲突。每部分声明字符集与传输编码。

### 4.4 可重复性

同一份输入必须产出同一份字节。boundary 的随机性只影响该次输出，不影响结构。纯 ASCII 的常规通知作为基线快照，用于防止无关重构改变报文形状。

## 5. 错误处理约定

- 所有校验错误通过 `error` 返回，调用方（`Compose`）向上传递。
- 错误文本说明被拒绝的逻辑字段与原因，但不回显完整原始值（避免把注入内容写进日志）。
- `Compose` 要么返回完整报文，要么返回错误，不返回半成品。

## 6. 测试策略

- 有测试覆盖正常路径：纯 ASCII 主题、单收件人、无附件。
- 规范文档 §9 的检查清单是后续测试的入口：每一项都应当有对应的可观察行为。
- 基线快照用于锁定纯 ASCII 报文的字节形状。
