# MIME envelope

This document defines how the generated `.ics` text is wrapped into a MIME
message before it is handed to the mail transport.

## 1. Message shape

The message is a `multipart/mixed` container with at least one part:

1. a `text/calendar; method=REQUEST; charset=UTF-8` part carrying the
   `.ics`, and
2. optionally an attachment part carrying the attachment description supplied
   by the front end.

A message with no attachment is still `multipart/mixed` with a single body
part; it is not downgraded to a bare `text/calendar` message.

## 2. Header serialisation

- Header lines are separated and terminated by CRLF.
- A header value is written as `Name: value`, with exactly one space after the
  colon.
- The end of the header block is the empty line CRLF CRLF.
- Header values must not contain a raw CR or LF. Values that would require one
  are rejected.
- Header values are not folded in this service.

## 3. The multipart boundary

### 3.1 Generation

- The boundary is generated by the service, not supplied by the client.
- The boundary must be unique for each message.
- The boundary consists only of characters permitted in a MIME boundary:
  `ALPHA / DIGIT / "'" / "(" / ")" / "+" / "_" / "," / "-" / "." / "/" /
  ":" / "=" / "?"` plus space. The service generates boundaries from a
  restricted subset of these (letters, digits, `-`, `_`, `.`).
- The generated boundary must be long enough, and include enough entropy,
  that accidental repetition within the message is not plausible.

### 3.2 Absence from the body

- The boundary string must **not** occur anywhere in any body part (neither
  the `.ics` text nor the attachment description), on a line by itself or as
  a substring.
- Before a boundary is used, the body is searched for it; if it occurs, a new
  boundary is generated and the check repeated. This applies to the prefixed
  forms as well: the delimiter lines are `--<boundary>` and the closing
  delimiter is `--<boundary>--`, and the search covers `<boundary>` in the
  body.
- Generation must terminate. A body constructed specifically to contain every
  candidate is pathological; the service generates a new candidate each round
  and bounds the number of rounds, rejecting the request if it cannot find a
  clean boundary.

### 3.3 Delimiters

- The start of the message body is `--<boundary>` CRLF.
- Each part begins with `--<boundary>` CRLF, followed by the part headers,
  then CRLF, then the part body.
- Parts are separated by CRLF `--<boundary>` CRLF.
- The container ends with CRLF `--<boundary>--` CRLF.
- A boundary delimiter always starts at the beginning of a line.

### 3.4 Boundary in the Content-Type header

- The boundary appears in the `Content-Type` header of the container as
  `boundary=<value>`.
- If the boundary consists only of token characters it is written bare;
  otherwise it is quoted. The service's generated boundaries are tokens, so
  they are written bare, but the header builder must apply the same quoting
  rule as for any parameter value (`params.md` §2.1) so that a boundary
  containing `=`, `?`, `/`, `:` or a space is still correct.

## 4. Line endings

- Every line in headers, delimiters, part headers and part bodies is
  terminated by CRLF. A bare LF must not appear anywhere in the message.
- The `.ics` text itself already uses CRLF (`ical.md` §2); the envelope must
  not rewrite it or append a bare LF after it.
- When the `.ics` text is placed in a part, it is followed by CRLF before the
  next delimiter.

## 5. Content transfer encoding

- The `.ics` part is sent as `8bit` (no transfer encoding transformation); the
  text is already UTF-8.
- The attachment description is sent as `text/plain; charset=UTF-8`, also
  `8bit`.
