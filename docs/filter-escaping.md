# ldapfence 设计说明与边界规范

本文说明 `ldapfence` 的职责、调用方与目录服务之间的契约，以及每一条边界上
「正确行为应该是什么」。本文只规定行为与错误语义，不规定实现方式。

## §1 定位与数据流

`ldapfence` 是公司目录服务与上游 LDAP 之间的中间层。三类调用方共用同一套出网通道：

| 调用方 | 入口 | 典型输入 |
|---|---|---|
| 员工登录 | `authenticate()` / `findUser()` | 工号（`uid`）、口令 |
| 组织架构同步 | `searchOrganization()` / `searchServiceAccounts()` | `ou` 名、分页大小 |
| 运维高级搜索 | `parseAdvanced()` / `advancedSearch()` | 管理员手写的过滤器、`base`、`scope` |

所有请求最终只会以两种形态离开本层：

1. **过滤器（filter）**——交给 `client.search(base, { filter, ... })`；
2. **可分辨名称（DN）**——交给 `client.bind(dn, password)`。

调用方输入永远属于不可信数据。本层的义务是：在数据变成 filter 或 DN 之前，
完成转义与准入校验，使调用方输入只能落在它被允许的语义位置内，无法改变
filter 的结构、DN 的层级，也无法把请求指向配置之外的命名上下文。

`client` 由调用方注入，本层只依赖两个方法：

- `client.search(base, options)` → `{ entries, pageCookie? }`
- `client.bind(dn, password)` → `{ dn }`

仓库内的 `createMockClient()` 是与真实客户端同形的进程内实现，用于测试与演示；
它不做任何额外防护，请求原样评估。因此凡是「本层没有拦住」的输入，都会在
mock 上表现出与真实服务端一致的效果。

### §1.1 配置

配置（`createConfig()`）至少包含：

- `suffixes`：允许作为搜索起点的命名上下文列表；
- `peopleSuffix` / `serviceSuffix`：员工与服务账号分别所在的子树；
- `search` / `advanced`：默认 `base`、`scope`、返回属性、分页大小、过滤器长度上限。

凡是「允许的 suffix」在本文中指 `suffixes` 中的条目（大小写不敏感，DN 按
RDN 序列逐段比较，值按大小写不敏感比较）。

## §2 过滤器中的值转义（RFC 4515）

### §2.1 适用面

任何由调用方提供的值进入 filter 之前都必须转义，包括但不限于：登录工号、
同步时的 `ou`、等值搜索的值、以及任何以字符串插值方式构造 filter 的辅助函数。

属性名（attribute description）不属于「值」，不得接受调用方任意字符串；
构造 filter 的辅助函数只接受合法的属性描述符。

### §2.2 必须转义的字符

值中下列字符出现时，必须写成反斜杠加两位大写或小写十六进制：

| 字符 | 转义结果 |
|---|---|
| `\`（反斜杠，U+005C） | `\5c` |
| `*`（U+002A） | `\2a` |
| `(`（U+0028） | `\28` |
| `)`（U+0029） | `\29` |
| NUL（U+0000） | `\00` |

反斜杠必须先被识别并转义，绝不能作为其他转义的一部分被「消费掉」；
`a\2a` 与 `a*` 是两个不同的值，前者在服务端按字面量 `a*` 匹配。

### §2.3 其他字节

0x00–0x1F、0x7F 以及非 UTF-8 合法编码的字节同样必须以 `\XX` 形式输出。
其余可打印字符原样输出。

### §2.4 结果保证

对一个用户值 `v`，`(attr=<escape(v)>)` 解析后必须恰好得到一个等值断言
（equality assertion），其值为 `v`。换言之：

- 输入中的 `*` 不得让该断言退化为 presence 或 substring；
- 输入中的 `)` / `(` 不得提前闭合当前断言或开启新的断言；
- 输入中的 `\` 不得吞掉紧随其后的合法转义；
- 因此，任何用户值只可能匹配零条或一条记录，绝不会变成通配。

### §2.5 复合结构的边界

由本层自己拼装的操作符（`&`、`|`、`!`）与括号可以出现在最终 filter 中，
但它们只能来自代码，不能来自调用方值。构造出的 filter 必须语法完整：
括号配对，运算符两侧结构合法。

## §3 DN 中的值转义（RFC 4514）

### §3.1 适用面

任何由调用方提供的值进入 DN 的 RDN 值（attribute value）之前都必须转义，
包括登录时拼装的 `uid=...,<peopleSuffix>` 与服务账号的 `cn=...,<serviceSuffix>`。

### §3.2 必须转义的字符

RDN 值中下列字符必须以反斜杠转义（`\,` `\+` `\"` `\\` `\<` `\>` `\;` `\=`）：

`, + " \ < > ; =`

此外：

- 值开头或结尾的**空格**必须以 `\ ` 转义；
- 值开头为 `#` 时必须转义为 `\#`；
- 空值必须写成空字符串并由调用方决定是否允许（本层不允许空工号登录）；
- NUL 及不可打印字符按 `\XX` 十六进制转义。

### §3.3 结果保证

拼装后的 DN 必须恰好由预期的 RDN 序列构成：

```
uid=<转义后的工号>,<peopleSuffix>
cn=<转义后的账号名>,<serviceSuffix>
```

也就是说，调用方值只能占用一个 RDN 的值位置：

- 值中的 `,` 不得把 DN 拆成额外的 RDN，从而把绑定目标移到其他组织单元；
- 值中的 `=` 不得让解析器把它识别成新的属性类型；
- 值中的 `\` 不得把后续字符吞成转义，从而改变值的实际内容；
- 值不得以 `#` 或前后空格造成与字面值不同的规范化结果。

DN 解析与比较本身要求：属性类型大小写不敏感，值在比较时按大小写不敏感处理，
RDN 顺序必须一致。

## §4 搜索起点的准入（base / scope）

### §4.1 base

`client.search()` 的 `base` 无论来自配置、调用方显式传入还是高级搜索参数，
都必须先做两件事：

1. 语法上是一个合法 DN（能被 §3 的解析规则解析）；
2. 位于 `config.suffixes` 中某个 suffix 之下（含相等）。

任一条件不成立时，本层必须直接抛出错误，**不得发起任何出网调用**。
允许的 suffix 之外的命名上下文（例如 `dc=evil,dc=com`）必须被拒绝，
错误信息中不得把整份允许列表回显给调用方。

### §4.2 scope

`scope` 只允许三个枚举值：

| 值 | 含义 |
|---|---|
| `base` | 仅 base 这一条 |
| `one` | base 的直接子条目 |
| `sub` | base 及其全部后代 |

任何其他值（大小写不同的写法也视为其他值）都必须直接抛出错误，
不得交给客户端，也不得静默替换成默认值。

### §4.3 默认值

未显式提供 `base` / `scope` 时使用配置中的默认值；默认值本身也必须满足
§4.1 与 §4.2。调用方提供的 `null` / `undefined` 视为未提供。

### §4.4 其余选项

`attributes` 只影响返回字段投影，不改变匹配范围；`sizeLimit` / `pageSize`
必须是非负整数。分页时本层负责携带 `pageCookie` 直至翻完所有页；
未开启分页时不得发送 `pageCookie`。

## §5 高级搜索过滤器的准入

高级搜索接受管理员手写的 LDAP filter 字符串。它不是「可信代码」，必须按
语法树逐节点审查后才能出网。

### §5.1 语法

- 过滤器必须以 `(` 开始、`)` 结束，括号配对；
- 支持：`(&...)`、`(|...)`、`(!...)`、`(attr=value)`、`(attr=*value*)`、
  `(attr>=value)`、`(attr<=value)`、`(attr~=value)`；
- 子串通配只允许出现在 `=` 中；`>=` / `<=` / `~=` 的值中不得含通配符；
- 属性名必须是合法属性描述符（字母头，只含字母、数字、连字符，可带 `;option`）；
- 值中的转义必须是 `\XX` 两位十六进制；未转义的控制字符视为语法错误；
- 语法错误必须被拒绝，错误应包含出错位置，且不得出网。

### §5.2 属性黑名单

过滤器语法树中，任何节点引用的属性不得为 `userPassword`（大小写不敏感），
也不得通过任何别名/选项写法绕过该限制。命中黑名单时整条过滤器被拒绝。

### §5.3 恒真结构

不得让「对任意条目都成立」的结构直接落到服务端。至少包括：

- `(| ... )` 中任一子过滤器为 presence（`(attr=*)`）或本身恒真；
- 空的 `(&)` 与空的 `(|)`（前者恒真，后者恒假，均视为无意义结构）；
- `(!(attr=...))` 之外，任何经化简后等价于 `(objectClass=*)` 的写法。

判定要求：在提交前对语法树做规范化（折叠嵌套、去掉冗余括号、识别空的
AND/OR），再做上述检查。命中时拒绝，不得改写成更窄的过滤器后继续执行。

更一般地，高级搜索的过滤器必须至少包含一个对具体属性值的**约束**，
不能只由 presence 与空逻辑组成。

### §5.4 长度与资源

过滤器的 UTF-8 字节长度不得超过 `advanced.maxFilterLength`；
超限拒绝。长度检查不能替代 §5.1–§5.3 的任何一项。

### §5.5 base / scope / 返回字段

高级搜索的 `base`、`scope` 同样受 §4 约束（包括调用方显式传入的值）。
返回属性若由管理员指定，只用于投影，不得借其读取黑名单属性；
若请求的属性集合与 §5.2 冲突，整条请求被拒绝。

## §6 错误语义与可观测性

### §6.1 错误分类

| 场景 | 错误码 |
|---|---|
| DN 语法非法 | `INVALID_DN_SYNTAX` |
| base 不在允许 suffix 下 / 不存在 | `NO_SUCH_OBJECT` |
| scope 非法、过滤器语法错误 | `PROTOCOL_ERROR` |
| 账号不存在、口令错误 | `INVALID_CREDENTIALS` |
| 超出长度、大小限制 | `SIZE_LIMIT_EXCEEDED` / `PROTOCOL_ERROR` |

错误对象携带 `code` 与只读的 `details`。面向调用方的 `message`
不得包含口令、完整 DN 列表或配置内部列表。

### §6.2 不得出网

§4 与 §5 中的准入失败必须发生在调用 `client.search` / `client.bind` 之前。
测试与运维可以用 `client.operations` 观察这一性质：出现拒绝时，
`operations` 不应新增条目。

### §6.3 可观测性

本层不对日志做强制要求；若开启调试输出，日志中的 filter 与 DN 应按已转义
形态记录，不得记录明文口令。

## §7 非目标

- 不实现 LDAP 协议本身（socket、BER 编解码、TLS）——由注入的客户端负责；
- 不做授权模型（谁能做高级搜索由上层网关决定）；
- 不缓存目录数据，不改变服务端的排序、分页与大小限制语义。
