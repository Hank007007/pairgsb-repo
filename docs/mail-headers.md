# 出站邮件报文规范

本文描述 headlace 产出的报文必须满足的规则。规范只定义「正确行为」，不规定实现方式。

## §1 适用范围

headlace 接收上游（营销、事务两类通知）交来的收件人列表、发件人、回复地址、退订地址、主题、纯文本正文、HTML 正文和附件，产出一份可直接交给 `net/smtp` 的 RFC 5322 报文。报文中的地址、显示名、主题、附件文件名都可能来自运营后台或终端用户，因此每一个进入报文的外来字符串都必须在进入前完成校验或转义。

## §2 头字段的语法约束

### §2.1 头名

头名（field name）只允许 `[A-Za-z0-9-]` 中的字符，且必须以字母或数字开头。不符合该规则的头名不得出现在报文中，组装过程必须以错误终止。

### §2.2 头值

头值中不得出现裸 CR（U+000D）或裸 LF（U+000A）。唯一允许的 CRLF 是折叠（folding）：CRLF 后紧跟一个空格或水平制表符。除折叠外头值中不得出现其他 C0 控制字符（U+0000–U+0008、U+000B、U+000C、U+000E–U+001F、U+007F）。

任何不满足上述条件的头值都意味着上游数据试图注入额外的头部行，组装过程必须返回错误，且错误信息应当指明是哪个逻辑头字段被拒绝；不得把原值降级处理后继续下发。

### §2.3 行长度

每一行（含折行后的续行）不超过 998 字节（不含行尾 CRLF）。可打印字符的推荐上限为 78 字节，超出时应当折叠。

## §3 RFC 2047 encoded-word

### §3.1 何时需要编码

非 ASCII 的头值必须用 RFC 2047 encoded-word 表示。ASCII 控制字符同样必须编码，不得原样输出。纯可打印 ASCII 且不含特殊字符的头值保持明文。

### §3.2 encoded-word 的格式与长度

每个 encoded-word 的形式为 `=?UTF-8?B?<base64>?=`（或 `Q` 编码），长度不得超过 75 个字符。一个过长的值必须拆成多个 encoded-word，encoded-word 之间以折行或单个空格分隔。

### §3.3 折行与字符边界

折叠必须发生在合法的切点上：不得在 UTF-8 多字节字符的字节序列中间切断，也不得把单词从中间切开（对无空格的 CJK 文本，允许在字符边界处切分）。多个相邻的 encoded-word 拼接后经解码必须字节还原原文。

### §3.4 解码自检

任何经过编码或折叠的头值，都应当能被 `net/mail` 的解析器还原为原值。无法还原即视为组装失败。

## §4 地址列表

### §4.1 分隔符

地址列表以逗号分隔，但引号字符串内的逗号、圆括号注释内的逗号不构成分隔符；尖括号内的 `@` 与逗号也不得影响列表切分。分隔符两侧的空白应被忽略。

### §4.2 地址的 local part 与域

`@` 只有在引号字符串之外、且位于尖括号内的地址规格（addr-spec）中才具有分隔意义。`"a@b"@example.com` 是一个合法地址，其 local part 是 `"a@b"`，域是 `example.com`。

### §4.3 注释

圆括号注释（含嵌套注释）属于可忽略的 CFWS。输出报文时注释必须被剥掉，不得原样回填进显示名或地址。

### §4.4 反解校验

每个地址在写进报文之前，必须能由 `net/mail.ParseAddress` 反解回同一地址；反解失败则整份报文组装失败。不允许为了迁就实现而放宽 `net/mail` 的输入。

## §5 显示名

显示名按 RFC 5322 的 phrase 规则输出：

- 只含 `atext` 与空格的显示名可以不加引号。
- 含 `"`、`,`、`;`、`<`、`>`、`@`、`.`、`:`、`\`、`[`、`]` 等特殊字符或首尾空白、连续空白的显示名，必须放进带引号的字符串（quoted-string）。
- quoted-string 内的 `"` 和 `\` 必须以反斜杠转义。
- 非 ASCII 显示名按 §3 编码。
- 地址的输出形式：无显示名时只输出 addr-spec，例如 `alice@example.com`；有显示名时输出 `显示名 <addr-spec>`。纯 ASCII 的常规地址保持这一形状，以维持基线快照的稳定性。

显示名转义后再解析回来必须与原显示名逐字符一致。

## §6 附件与 Content-Disposition

### §6.1 何时使用 filename*

附件文件名全部落在 `attr-char` 集合（RFC 2231/5987 定义）之内、且不含 `"`、`\`、`;`、控制字符时，可以直接用 `filename="..."`。

### §6.2 RFC 2231 编码

文件名含非 ASCII 字符、或含 `"`、`\`、`;`、控制字符、换行时，必须使用 `filename*=UTF-8''<percent-encoded>` 形式。百分号编码使用大写十六进制，除 attr-char 外的每个字节都要编码。

### §6.3 可逆性

解析端按 RFC 2231 解码 `filename*` 后得到的原始文件名必须与上游给出的字符串逐字节一致。文件名中的 CR/LF 不得以任何形式出现在头部行中。

## §7 正文与多部分结构

- 含 HTML 正文或附件时使用 `multipart/mixed`（或 `multipart/alternative` 嵌在 `multipart/mixed` 中，具体层级由实现决定，但必须能让常见客端正确展开）。
- 每个 part 的 `Content-Type` 必须带 `charset=utf-8`（文本部分）。
- 附件以 base64 传输编码表示，`Content-Transfer-Encoding: base64`。
- 纯文本正文中的空行不构成额外的 MIME 分隔；boundary 的生成必须保证不与正文内容冲突。

## §8 组装入口的职责

`Compose` 是唯一出口，必须对每一个进入报文的值负责：

- 主题、发件人、收件人、显示名走 §3/§4/§5。
- `Reply-To` 与 `List-Unsubscribe` 与普通地址头适用同一套规则；带控制字符或无法按 §4.4 反解的值必须导致组装失败。
- 任一环节返回错误时，`Compose` 必须返回错误，不得返回部分报文。

## §9 合规性检查清单

1. 报文中的所有头名匹配 `^[A-Za-z0-9][A-Za-z0-9-]*$`。
2. 去掉折叠后续行之后，头块中不出现裸 CR/LF。
3. 每一行 ≤ 998 字节。
4. 每个 encoded-word ≤ 75 字符，拼接后解码等于原值。
5. 地址列表切分正确，注释已剥离。
6. 每个地址能被 `net/mail.ParseAddress` 反解。
7. 附件文件名按 §6 处理且可逆。
8. 纯 ASCII 常规通知的输出与基线快照逐字节一致。
