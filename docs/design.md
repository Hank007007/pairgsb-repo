# 设计说明

本文描述 StowSign 各部分的职责、数据流与「正确行为」应当满足的性质。规范细节以
`presign-spec.md` 为准；本文只讲结构与边界，不含实现。

## 1. 目标

- 签发端与校验端共享同一个签名契约，双方独立实现也能互认。
- 签名绑定：HTTP 方法、资源路径、全部查询参数（除签名本身）、被点名的 header
  的值。
- 策略在签发与校验两端都生效：签发端拒绝越权申请，校验端拒绝越权请求。
- 所有判定默认拒绝：输入缺失、无法解析、超出上限，都落在拒绝一侧。

## 2. 数据流

```
policy(JSON) ──> Policy ──┐
                          ├─> presign() ─> Grant(url, method, resource, expires)
method / resource / ttl ──┘                         │
                                                    │  交给客户端
                                                    ▼
HTTP 请求 ──> verify(method, path, query, headers, client_ip, policy) ──> VerifiedRequest
```

签发端产出的 URL，其查询参数是校验端唯一的元数据来源。两端的约束是：

- 校验端不得依赖签发端写入参数的顺序。
- 校验端不得信任 URL 中任何未参与签名的字段。
- 签发端不得输出校验端无法重新推导的信息。

## 3. 模块职责

### `canonical.py`

纯函数集合，不持有状态，不读取环境。

- `percent_encode`：把任意值编码成 RFC 3986 非保留字符集之外的百分号形式。
- `canonical_query`：把查询参数对转换成一个确定的规范字符串。**性质**：输出
  只取决于参数集合（多重集），与输入顺序无关；不同的线上字节（如 `%2F` 与
  `/`）必须得到不同输出；签名参数自身不参与。
- `canonical_headers`：把签名 header 名与其值转换成一个确定的块。**性质**：
  名字大小写不敏感、顺序无关；值的首尾空白与内部空白被归一；同名多值按出现
  顺序合并。
- `header_digest`：块的 SHA-256。
- `build_canonical_request`：把方法、路径、规范查询串、header 摘要拼成待签名
  文本。
- `compute_signature`：HMAC-SHA256。

路径按 URL 中原样字节进入规范请求，不做解码；路径里的 `%2F` 是键的一部分。

### `policy.py`

- `Policy.from_dict`：解析策略文档，归一字段（方法大写、header 名小写、资源
  去首尾斜杠），拒绝未知版本与错误类型。
- `check_method`：方法维度。空列表 = 不限；否则命中任一即通过。
- `check_resource`：资源维度。**正确语义**是路径段边界上的前缀：前缀 `P` 覆盖
  `P` 本身与 `P/...`，不覆盖任何其它以 `P` 开头的键。多前缀之间是 OR。
- `check_ip`：来源网络维度。IPv4 与 IPv6 均须支持，按地址族比较；地址缺失或
  无法解析时必须拒绝（在策略确实配置了网络限制的前提下）。
- `check_required_headers`：策略要求签名的 header 必须都出现在签名名单里。

各维度之间是 AND；同一维度内多个取值之间是 OR。

### `clock.py`

- `now_ts`：返回整数 Unix 秒，可注入。
- `expires_at`：签发时算出绝对截止时刻。
- `is_expired`：把 URL 中记录的截止时刻与当前时刻比较。**性质**：判定只依赖
  两个绝对时刻，不依赖调用次数或调用间隔；同一 URL 的截止时刻在签出后不再
  移动。

签发时长上限是策略之外的硬约束，应在签发时执行，而不是在校验时截断。

### `grant.py`

- 校验方法与资源（复制场景还要校验目标资源）。
- 校验策略要求的 header 都已提供。
- 计算 header 摘要，冻结截止时刻。
- 组装查询参数与路径，签名，返回 `Grant`。
- 对外返回的 URL 参数名固定，不得改名。

服务端复制场景下 `X-Stow-Target` 是必填的第二资源；源与目标都必须被策略覆盖。

### `verify.py`

按顺序：

1. 检查算法标识。
2. 用 URL 中记录的绝对截止时刻判定过期。
3. 依据签名名单，用**请求实际携带的 header 值**重算 header 块摘要，并与 URL
   中记录的摘要比较。缺失 header 或摘要不符都拒绝。
4. 若提供了策略，则校验方法、资源、目标资源、来源网络。
5. 用规范请求重算签名，常量时间比较。

**关键性质**：

- 同一个请求重排查询参数，第 5 步仍应得到同一个签名。
- 改动任一被签字段（包括 header 值、编码写法）都应使第 3 或第 5 步失败。
- 校验端不应先解码再做任何比较。

## 4. 错误模型

所有失败派生自 `StowSignError`：

| 异常 | 触发 |
|---|---|
| `PolicyError` | 方法/资源/目标/来源网络/必需 header 不满足策略 |
| `SignatureError` | 算法不支持、签名 header 绑定不成立、签名不匹配 |
| `ExpiredError` | 已过绝对截止时刻 |

校验端对外只暴露失败与原因类别，细节写入日志。

## 5. 测试策略

测试分两层：单元测试直接驱动纯函数（编码、规范串、策略判定、时间判定），集成
测试用 `presign` 签出 URL 再交给 `verify` 走完整路径。集成测试应覆盖不同来源
地址族、不同路径形态、不同 header 组合以及跨越截止时刻的校验。注入 `now`
可以让时间相关用例保持确定性。
