# hopfence 转发规范

本文件定义 hopfence 在转发一个请求时必须满足的行为。文中「必须」「不得」均为规范性要求；具体实现不受约束，但对外可观察的效果必须一致。

请求在 hopfence 内的处理顺序固定为：

1. 确定客户端地址（§2）
2. 解码请求路径（§3.1）
3. 按解码后的路径选择路由（§4）
4. 相对所选路由清理路径，并执行路由 ACL（§3.2、§5）
5. 构造发往上游的请求头（§6）
6. 转发请求、回写响应
7. 写一条访问日志（§7）

## §1 上游与路由的边界

- 上游只来自配置。请求头、查询参数、Cookie 都不得影响最终选中的上游。
- 路由只来自配置。请求不得新增、删除或重排路由，也不得改变路由的匹配前缀。
- 一条请求最多命中一条路由。未命中任何路由时返回 `404`。
- 路由 ACL 拒绝时返回 `403`，且请求不得发往上游。

## §2 客户端地址

- 客户端地址只取 TCP 连接的对端地址。除此之外的任何来源都不得参与判定。
- 入站请求里已有的 `X-Forwarded-For` 必须整体丢弃，不得取用其中任何一段，也不得把它拼接到新值前面。
- 发往上游的请求必须带有且只带一条 `X-Forwarded-For`，其值是本次 TCP 对端的 IP 字面量（IPv6 使用不带方括号和端口的形式）。
- 访问日志中记录的客户端地址必须与发往上游的 `X-Forwarded-For` 相同。
- 对端地址无法解析为 IP 时，返回 `500`，请求不得发往上游。

## §3 路径解码与清理

### §3.1 解码

- 路径必须按百分号解码一次；解码失败（非法转义）时返回 `400`。
- 任何编码形式（`%2e`、`%2E`、`%2f`、`%252e` 等）都必须先解码再判断，不得在码形态上直接做前缀比较。
- 解码只做一次，不递归解码。
- 解码只作用于路径，不得改动查询字符串。

### §3.2 清理

清理是对解码后的路径按段进行的处理：

- 空段（连续的 `/`）与 `.` 段被移除；
- `..` 段回退一层；
- 结尾的 `/` 保留与否不影响任何判断；
- 清理结果以 `/` 开头。

清理不得让路径逃出所选路由的前缀。判定方式是：把所选路由的前缀剥离后处理剩余段，若某个 `..` 需要退到前缀之上，该请求必须由所选路由拒绝（`403`），不得改投其他路由，也不得交给任何上游。

因此 `/static/%2e%2e/admin` 的路径是：解码后为 `/static/../admin`，选中前缀 `/static`，相对该前缀清理时 `..` 越出前缀根，结果是 `403`。这个请求不会被 `/static` 路由转发，也不会被转交给 `/admin` 路由。

清理结果在整条链路上保持一致：`deny_paths` 比较、转发给上游的路径、访问日志中的路径，都用同一个清理结果，不得出现「判定用一套、转发用另一套」。

## §4 路由选择

- 选路使用 §3.1 解码后的路径，且发生在 §3.2 的 `..` 回退之前；选路不得使用已经做过 `..` 回退的路径。
- 在前缀匹配的路由中，选择前缀最长的一条；前缀等长时以配置顺序靠前者为准。
- 前缀匹配以路径段为界：前缀 `/static` 匹配 `/static` 和 `/static/a`，不匹配 `/staticx`。
- 前缀本身在配置加载时已校验，按原样参与比较。

## §5 路由 ACL

- 允许列表 `allow` 非空时，客户端地址必须落在其中某个前缀内；否则拒绝。
- 拒绝列表 `deny` 非空时，客户端地址落在其中任一前缀内即拒绝；`deny` 优先于 `allow`。
- 路径排除项 `deny_paths` 按路径段前缀匹配，语义与 §4 的前缀匹配一致：排除 `/admin` 时，只拒绝 `/admin` 及其子路径（例如 `/admin/ops`），不得连带拒绝 `/admin-backup`、`/administrator` 这类同字符串前缀但不同路径段的路径。
- 路径排除项的比较必须使用 §3.2 清理之后的路径，并以路径段为界；不得用裸字符串前缀代替路径段判断。
- 地址一律按 IP 比较，IPv4 与 IPv4-mapped IPv6 视为同一地址。

## §6 转发请求头

### §6.1 逐跳头

以下头部是逐跳头，不得转发给上游：

`Connection`、`Keep-Alive`、`Proxy-Authenticate`、`Proxy-Authorization`、`TE`、`Trailer`、`Transfer-Encoding`、`Upgrade`

此外，`Connection` 头中按逗号分隔列出的每一个头名字段，也必须在本次转发中被视为逐跳头并丢弃。头名比较不区分大小写，并忽略首尾空白。

「逐跳」是针对最终发往上游的头集合判定的：被 `Connection` 点名的头不得出现在上游请求里，也不得以任何形式影响其他头的转发；没有出现在 `Connection` 中的同名头仍按普通头处理。

### §6.2 客户端身份相关头

- 入站 `X-Forwarded-For` 按 §2 处理。
- `X-Real-IP` 只由 hopfence 写入，入站值不得透传。
- 其余端到端头（`Authorization`、`Content-Type`、自定义业务头等）按原样转发，除非它们是 §6.1 定义的逐跳头。

### §6.3 消息体与响应

- 请求体与响应体按原样流式转发，不得缓冲整个消息体后再发送。
- 响应状态码与端到端响应头回写给客户端；§6.1 固定列表中的响应头不得回写。
- 上游不可达或超时时返回 `502`。

## §7 访问日志

每次请求结束后写且只写一行，字段顺序固定为：

```
客户端地址 方法 清理后的路径 状态码 用户代理
```

- 字段之间以一个空格分隔。
- 客户端地址、方法、路径、用户代理中的以下字节必须转义为 `%` 加两位大写十六进制（按 UTF-8 字节逐个处理）：
  - 空格（`0x20`）；
  - 所有控制字符（`0x00`–`0x1F`、`0x7F`），包括换行、回车、制表符；
  - `"`（`0x22`）、`%`（`0x25`）、`\`（`0x5C`）。
- 转义后这些字节约占三个字节，其他字节原样输出；不含上述字节的字段按原样输出，不加引号、不加包裹。
- 由此保证一个请求恰好产生一行，该行按「单个空格」切分恰好得到 5 个字段，且转义可逆。
- 路径字段必须记录 §3.2 清理之后的路径。
- 状态码为三位十进制数字。
- 日志写入不得因为字段内容而抛错或截断请求处理。

## §8 错误响应

| 情形 | 状态码 |
|---|---|
| 非法百分号转义 | 400 |
| 未命中路由 | 404 |
| 路由 ACL 拒绝（含 `..` 越出前缀） | 403 |
| 对端地址无法解析 | 500 |
| 上游不可达或超时 | 502 |

错误响应体不得回显请求中的原始路径、头或其他客户端可控内容。
