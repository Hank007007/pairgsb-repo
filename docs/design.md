# frameseal 设计说明

本文说明 frameseal 的模块划分、数据流与各环节「正确行为应当是什么」。协议数值与关闭码以 `docs/frame-rules.md` 为准；本文只描述职责与边界，不描述具体实现方式。

## 1. 定位

frameseal 是自研网关的 WebSocket 前端解码器。它只负责**收**：把客户端送来的字节流还原成一条条消息与控制事件，交给业务 handler。连接的建立（HTTP Upgrade）、扩展协商结果的传递、以及把 close 帧写回对端由网关的其他部分完成。

不直接使用通用 WebSocket 库的原因：

- 网关前端面对外部客户端，需要按 `docs/frame-rules.md` 的口径做更严格的收帧约束；
- 审计、重放与抓包比对接的是**线上原始字节**，要求解码过程不改写调用方的缓冲区；
- 资源上限与关闭码要能按网关自己的口径统一处理。

## 2. 模块划分

| 模块 | 职责 |
|---|---|
| `src/frame.js` | 从字节流前部解出一帧：帧位、长度、mask、payload |
| `src/fragment.js` | 把数据帧组织成消息，维护消息边界与累计量 |
| `src/control.js` | ping / pong / close 的结构检查与解释 |
| `src/permessage.js` | permessage-deflate 的协商结果与消息解压 |
| `src/text.js` | 文本消息的字符校验与交付 |
| `src/conn.js` | 连接状态机：接收缓冲、事件分发、关闭流程 |
| `src/errors.js` | 协议错误类型与关闭码携带 |
| `src/limits.js` | 网关资源上限常量 |
| `src/opcodes.js` | 操作码常量与分类 |

## 3. 数据流

```
字节流 ──feed──▶ 接收缓冲
                   │
                   ▼
              parseFrame（逐帧）
                   │  frame { fin, rsv1..3, opcode, masked, mask, payload }
                   ▼
           ┌───────┴────────┐
           ▼                ▼
     控制帧处理         MessageAssembler
     (control.js)      (fragment.js)
           │                │  message { opcode, payload, compressed }
           ▼                ▼
     onPing/onPong/    解压（permessage.js，仅压缩消息）
     onClose/close          │
                            ▼
                     文本校验（text.js，仅 text 消息）
                            │
                            ▼
                        onMessage
```

要点：

- 解析以「一帧」为单位推进，只有完整帧才推进缓冲位置。
- 控制帧与数据帧走不同分支；控制帧在任何时候都不进入消息重组。
- 消息的边界由数据帧的 `FIN` 决定，不由调用时机决定。
- 解压发生在整条消息重组完成之后，且只对「起始帧声明了压缩」的消息进行。
- 文本校验发生在解压之后、交付之前。

## 4. 各环节的正确行为

### 4.1 帧解析

- 长度按 `docs/frame-rules.md` §1 读取：长度码、2 字节扩展、8 字节扩展三种形态，64 位扩展长度完整参与计算。
- 非法的长度形态（最高位为 1、高 32 位非零、超过单帧上限）在产出帧之前就被拒绝，并以对应的关闭码结束连接。
- 客户端帧必须带 mask；解 mask 的结果必须是新的一份 payload，调用方传入的字节保持原样（§2）。
- 未协商扩展时 RSV 位必须为 0；协商了 permessage-deflate 时只有起始数据帧的 RSV1 可以置位（§3）。
- 缓冲区不足时返回「尚未收完」，不产出残缺帧。

### 4.2 分片重组

- 重组器显式记录「当前是否处于一条消息中」，起始帧与 continuation 的配对关系须成立。
- 消息在收到 `FIN=1` 的数据帧时结束并产出。单帧消息（起始帧同时 `FIN=1`）立即产出。
- 控制帧不改变重组状态，也不把 payload 混入消息。
- 累计总长与帧数在追加之前检查，超限时中止重组并报告「消息过大」，已缓存内容不得继续增长（§4.7、§9）。
- 压缩标记取自起始帧的 RSV1，并随消息一起交给解压环节。

### 4.3 控制帧

- 控制帧必须 `FIN=1` 且 payload 不超过 125 字节。
- close 的 payload 结构、状态码集合与 reason 的 UTF-8 合法性按 §6 检查。
- ping 与 pong 的 payload 原样交给上层；不参与文本校验。

### 4.4 解压

- 是否解压只看消息起始帧的 RSV1（§8.2）。
- 解压有输出上限，达到上限即停止并报告「消息过大」，不能先展开再判断大小。
- 解压必须确认输入在 sync-flush 尾巴处恰好结束；截断、多余字节、尾巴不匹配都算协议错误（§8.5）。
- 解压失败不能把部分结果当作消息交付。

### 4.5 文本校验

- 对整条消息做一次严格 UTF-8 校验，分片边界可以落在多字节字符中间。
- 校验不能依赖「先宽松解码再检查替换字符」，因为那样无法区分真实 U+FFFD 与非法序列。
- 文本中的 `0x00` 一律拒绝。
- 校验失败时不交付任何结果。

### 4.6 连接状态

- 状态只有 `open → closing → closed` 三个。
- 只有 `open` 状态接受输入。
- 任何协议/载荷错误都走同一套关闭流程：记录关闭码与原因、把状态推进到 `closed`、通过 `onClose` 报告，并让 `feed` 抛出错误给调用方。
- 连接终止时，重组器中尚未交付的内容通过 `flush` 导出，不静默丢弃。

## 5. 错误与关闭码

`src/errors.js` 定义三类错误，它们都携带关闭码，便于连接层统一处理：

- `ProtocolError` → 1002（帧结构、mask、RSV、分片顺序、控制帧结构、压缩流结构、close 结构）
- `InvalidPayloadError` → 1007（文本 UTF-8、文本 NUL、close reason UTF-8）
- `MessageTooLargeError` → 1009（单帧、消息总长、帧数、解压输出）

上层根据错误的关闭码决定写给对端的 close 帧；本类只负责报告，不写 socket。

## 6. 测试策略

`test/` 用内存 Buffer 直接构造线上字节，不建立真实 socket：

- 帧构造只依赖 `testlib/frames.js` 里的纯函数；
- 单测覆盖帧头解析、消息组装、控制帧解释、扩展协商与文本解码；
- 连接层用例通过 `feed` 推入一个或多个帧，断言回调收到的消息与控制事件。

增用例应覆盖 `docs/frame-rules.md` 中尚未被覆盖的条款。
