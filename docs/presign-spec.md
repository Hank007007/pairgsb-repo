# StowSign 预签名规范 v1

本文件定义 StowSign 签名串的构造方式与校验规则。它是签发端与校验端之间的
唯一契约：只要两端都按本规范实现，任何一端生成的 URL 都能被另一端独立复算。

文中出现的「规范请求」指一段以换行符 `\n` 分隔的文本，签名是对它的 HMAC。

## 1. 组成

一条预签名 URL 由三部分构成：

- 资源路径：对象键（object key）原样拼在 endpoint 之后，段分隔符为 `/`。
- 查询参数：承载算法、截止时间、签名等元数据。
- 签名：对规范请求的 HMAC-SHA256，小写十六进制。

保留参数名（不得改名）：

| 参数 | 含义 |
|---|---|
| `X-Stow-Algorithm` | 固定为 `STOW-HMAC-SHA256` |
| `X-Stow-Expires` | 授权失效的绝对时刻，Unix 秒（UTC） |
| `X-Stow-SignedHeaders` | 参与签名的 header 名，逗号分隔，小写 |
| `X-Stow-HeaderDigest` | 签名 header 块的 SHA-256（小写十六进制） |
| `X-Stow-Resource` | 被授权的资源前缀下的具体键 |
| `X-Stow-Target` | 仅服务端复制（copy）场景出现，目标资源的键 |
| `X-Stow-Signature` | HMAC-SHA256 签名 |

## 2. 百分号编码

- 只保留 RFC 3986 的非保留字符：`A-Z a-z 0-9 - _ . ~`。
- 其余字符（含 `/`、空格、`+`、`=`、`&`、`%`）一律编码为大写十六进制，
  例如 `/` → `%2F`，空格 → `%20`。
- 编码是一次性、不可逆地施加在原始字节上的。**不允许**先解码再比较：
  `%2F` 与 `/` 是两个不同的输入，签出来的结果必须不同。

## 3. 规范查询串

1. 取出请求中的全部查询参数对，**保留其在请求行中的原始百分号编码形式**，
   不先解码、也不二次编码；剔除 `X-Stow-Signature`。
2. 以原始 key 作主键、原始 value 作次键，按字节序升序排列。
3. 以 `key=value` 拼接，对之间用 `&` 连接。

因此，同一条 URL 的参数无论以什么顺序出现在请求行里，规范查询串都相同，
签名也应相同。校验端不得假定参数顺序与签发时一致。因为保留原始编码，
`%2F` 与 `/` 会得到不同的规范串（见 §2）。

## 4. 规范 header 块

1. 取 `X-Stow-SignedHeaders` 列出的名字，统一转小写、排序。
2. 对每个名字，取请求中对应的全部值，按出现顺序以 `,` 连接；每个值先去掉
   首尾空白，再把内连续空白折叠为一个空格。
3. 每行写作 `name:value\n`，块以换行结尾。
4. `X-Stow-HeaderDigest` = 该块 UTF-8 字节的 SHA-256 十六进制。

header 的**值**是签名输入的一部分。校验端必须用请求上实际携带的 header 值
重新计算这个块，再与 URL 中记录的摘要比对；仅检查 header 是否存在是不够的。

## 5. 规范请求

```
STOW-HMAC-SHA256
<大写 HTTP 方法>
<URL 中的路径，未经解码>
<第 3 节的规范查询串>
<第 4 节的 header 摘要>
```

四行之后再无内容（不追加结尾换行）。签名 = `HMAC-SHA256(secret, 规范请求)`
的小写十六进制。

## 6. 有效期

- `X-Stow-Expires` 是**签发那一刻确定的绝对时刻**（Unix 秒），写入 URL 后
  不再变化。
- 校验时把当前时间与该值比较：当前时间 `>=` 该值即视为失效。
- 校验端不得把该值解释成「剩余秒数」或「从此刻起多久」。
- 签发端单次请求的授权时长上限为 7 天（604800 秒）；超过上限的签发请求
  必须被拒绝，而不是被截断后静默签发。

## 7. 路径前缀匹配

策略里的 `resources` 给出被授权的路径前缀。前缀 P 覆盖的键集合是：

- 键恰好等 P；或
- 键以 `P/` 开头。

即 `photos` 覆盖 `photos` 与 `photos/2024/cat.jpg`，但**不覆盖**
`photos-evil/x.jpg`、`photos.bak`。匹配以路径段为边界，不是裸字符串前缀。

## 8. 策略条件

策略文档字段（不得改名）：`version`、`methods`、`resources`、`ip_cidrs`、
`signed_headers`。

- 空列表表示该维度不作限制。
- 同一维度内多个取值之间是 OR：命中任意一条即通过。
- 不同维度之间是 AND：方法、资源、来源网络、必需 header 必须同时满足。
- 服务端复制场景下，`resources` 必须同时覆盖源（`X-Stow-Resource`）与
  目标（`X-Stow-Target`）。
- `signed_headers` 列出的 header，调用方必须提供值且必须被绑进签名。

## 9. 来源地址

`ip_cidrs` 同时接受 IPv4 与 IPv6 的 CIDR 写法，来源地址按同一族比较。
IPv4-mapped 的 IPv6 地址按其映射到的 IPv4 地址处理。取不到来源地址（缺失、
无法解析）时，带 IP 限制的策略一律判为不通过——宁可误拒，不可误放。

## 10. 校验顺序

1. 校验算法标识。
2. 校验有效期。
3. 校验签名 header 是否存在、header 值重算出的摘要是否与 URL 一致。
4. 按策略校验方法、资源、目标资源、来源地址。
5. 复算签并做常量时间比较。

任何一步失败都必须整体拒绝，且不得把失败原因泄露给调用方之外的日志之外的地方。
