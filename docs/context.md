# 上下文绑定

上下文（context）是调用方随加密请求附带的一组字符串键值对，用来把密文绑定到语义位置，例如「这个租户的、这个字段」。密钥可以复用，上下文保证密文不能被挪到别处使用。

## §3.1 序列化

上下文是一组字符串键值对。序列化为字节串的规则：

1. 每一项写成 `k=v`。
2. 各项之间以换行符 `\n` 连接，形成一个按行分隔的文本。
3. 行按 **key 的字节序**（UTF-8 编码后的字节）升序排列。排序在转义之前按原始 key 进行，保证同一组键值对无论以何种顺序传入，序列化结果都相同。
4. key 和 value 中的 `\n` 与 `=` 必须转义，使得转义后的文本可以被无歧义地反解。
   - 例如 `\n` 写作 `\\n`，`=` 写作 `\\=`。
   - 转义必须发生在拼接之前，顺序是先转义、后拼接。
5. 序列化结果对同一组键值对必须唯一。

由此推出：`{"a": "1\nb=2"}` 与 `{"a": "1", "b": "2"}` 不能序列化成同一串；前者是两项中的一项 value 里含换行和等号，后者是两项。

## §3.2 绑定到密文

序列化后的字节串不直接写入 blob 头，而是作为加密层绑定信息的一部分参与认证（见 `blob-format.md` §1.4）。绑定信息在加密时由调用方提供的 context 决定，在解密时由调用方提供的 context 重建并比对。

## §3.3 不匹配必须报错

解密时，调用方提供的 context 与 blob 绑定的 context 不一致，解密必须失败，错误码为上下文不匹配，**不得返回明文**。

- 多一个键、少一个键、某个值不同，都算不匹配。
- 不匹配的判断必须基于 §3.1 的规范序列化结果，而不是调用方传入字典的插入顺序或原始 Python 对象。

## §3.4 缺失与空

"没有提供上下文"和"提供了空上下文"是两种不同的输入：

- 未提供上下文（请求中该字段缺省）与提供了 `{}`（空字典）必须在行为上区分开。
- 一个不带上下文加密出来的 blob，不能用空上下文解开；一个带空上下文加密出来的 blob，不能用"未提供上下文"解开。
- 实现上，这一区别需要在请求解析、绑定值构造与序列化各层保持一致，不能因为空字典序列化成空串而与"没有上下文"共用同一个表示。
- "是否提供了上下文"是一个独立于序列化文本的事实，必须与序列化文本本身分开携带。

## §3.5 与 rewrap 的关系

rewrap 不解原 context（见 `key-lifecycle.md` §2.8）：它复用源 blob 中已经绑定的那份 context 信息，而不是重新序列化调用方在 rewrap 请求里给出的 context。若实现把 context 以某种形式存进了 blob 或可从 blob 恢复，rewrap 必须从 blob 取；不得依赖调用方重传。
