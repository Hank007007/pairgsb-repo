# 越权事件复盘

本文件收录两起已上线的越权事件。复盘结论已经转化为 `docs/authz-semantics.md` 中的规范条款。

## INC-1041：通过 `pods/exec` 进入生产容器

**发现方式**：例行审计发现某业务账号在生产 namespace 中对 `pods/exec` 的调用成功，而该账号只被授予过 `pods` 的读权限。

**经过**：

- 该账号绑定的角色含一条 `resources: ["pods"]`、`verbs: ["get"]` 的规则。
- 控制面在比较资源时按前缀处理，`pods` 被视为命中 `pods/exec`，于是 exec 请求被放行。
- 同一周内另一起误放行来自相反方向：某运维角色使用 `resources: ["*"]` 想覆盖全部资源，但 `*` 的匹配没有覆盖带子资源的请求，导致该角色在 `pods/log` 上被判 no-opinion，用户转而使用了一个权限更大的旧角色。

**结论**：

- 子资源必须作为独立资源标识授权，`pods` 与 `pods/exec` 互不蕴含（§2）。
- `*` 必须覆盖包括子资源在内的全部资源（§3.2）。

**影响**：生产 namespace 中一个容器被非授权账号进入；已轮换相关凭据。

## INC-1052：集合级请求绕过 resourceNames 限制

**发现方式**：数据平台反馈某用户能列出整个 namespace 的对象清单，而该用户只应看到单个数据库实例。

**经过**：

- 角色规则为 `resources: ["pods"]`、`resourceNames: ["db-prod"]`、`verbs: ["get", "list"]`。
- list 请求不带对象名。控制面在请求名为空时跳过了 `resourceNames` 检查，规则被判定为命中，用户拿到整个 namespace 的 pod 列表。
- 同一时期还观察到两处放大问题：重新加载角色后旧判定仍被返回；用户 A 的 allow 在用户 B 的相同请求上被复用。两者都让上述问题在修复配置后继续存在。

**结论**：

- 写了 `resourceNames` 的规则对名字为空的集合级请求不生效（§4.2）。
- 快照版本变化必须使旧判定失效（§7.2），缓存不得跨主体复用（§7.3）。

**影响**：namespace 内对象名称与镜像信息泄露；未发现进一步写入操作。
