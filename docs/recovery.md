# recovery.md — journal 与进程重启后的续跑

轮换的过程中随时可能被杀掉。本文规定「做什么之前先记什么」以及「重启之后怎么接着做」。

## §1 journal 是什么

journal 是一个按顺序追加的记录流，每个批次一份。它记录的是**编排器的意图与观察**，
不是供应商那边的权威状态——权威状态永远在供应商那边。

## §2 记录

### §2.1 写在前

**每一个会改变外部状态的步骤，都必须在动手之前先把它打算做什么写进 journal。**
「改变外部状态」包括但不限于：在供应商那边建 key、停 key、向消费者推送 webhook。

一条记录至少包含：批次名、key 名、动作、阶段、以及可供人工追查的引用信息。
外部动作完成之后可以再补一条结果记录（成功/失败/返回摘要），但**意图记录必须先落盘**。
「先」的意思是：在发起那次外部调用之前，这条记录已经完整写在磁盘上。

先写意图的意义：进程如果在动作执行到一半时死亡，重启后能知道「这一步可能已经在供应商
那边生效了」，从而按 §3.3 去核对，而不是当作没发生、再建一把。

### §2.2 追加、完整、可恢复

- 追加语义：新记录写在末尾，既有记录不被改写。
- 每条记录必须完整落盘（写穿到文件、刷新缓冲）之后，才允许发起对应的外部动作。
  一条只写了一半的记录，在重启后必须能够被识别并丢弃，而不是被当成有效记录。
- 进程被杀在任何时刻，journal 都必须留下「最后一个完整记录之前」的一致前缀：
  不能因为一次写入覆盖掉之前所有记录。

### §2.3 不得存明文

journal 里**不得出现 key 的明文**（新 key 或旧 key 的 secret 都不行），只能存引用：
供应商内部的 key id、本地引用号、哈希前缀等。journal 可能被复制到工单、日志、
备份里，明文等同于泄漏。

### §2.4 记录形状

一条记录是一个 JSON 对象（一行一条），字段：

| 字段 | 含义 |
|---|---|
| `batch` | 批次名 |
| `key` | key 名，例如 `signer.prod` |
| `action` | `create` / `notify` / `revoke` / `verify` / `rollback` |
| `phase` | 该 key 在写这条记录**之后**预期所处的阶段，取值见 `swap-window.md` §1 |
| `detail` | 自由结构，只能放引用，不得放 secret |
| `ts` | 写入时刻 |

## §3 重启后的续跑

### §3.1 入口

`resume()` 读入 journal，产出一个可以交给执行器继续使用的计划：哪些 key 处于哪个阶段、
下一步该做什么。

### §3.2 已完成的不重复做

阶段为 `revoked`（旧 key 已停）或 `rolled_back` 的 key 已经结束，续跑时不得再次为它
创建新 key、也不得再次向消费者推送。

### §3.3 做到一半的，先去供应商核对

阶段处于「做了一半」的位置时（典型情况：`created`——建新 key 的**意图**已记录，但无法
确定供应商那边是否真的建成了；或 `notified`——已记录推送，但不确定推送是否已经全部
送达），续跑必须：

1. 先向供应商读取**真实**状态（adapter 的 `describe`）；
2. 若新 key 实际已经存在，就**沿用**它，不得再建一把；
3. 若新 key 实际不存在，才可以（在重新写入意图记录之后）新建；
4. 若推送与回执已经完成，就跳过推送，直接进入双活判定。

### §3.4 回滚与续跑的边界

- 若批次已经被判定失败并完成回滚（阶段 `rolled_back`），重启后不得「续」出一批新的
  外部动作；它需要人重新发起一次批次。
- 已经停掉的旧 key 无法通过回滚恢复成可用状态；回滚只负责把**本批新建**的 key 回收，
  并把批次状态如实标记为失败。
- 已经建立的双活窗口不因进程重启而重新计时：`dwell` 的起点始终是 §1.3 所定义的
  「新 key 建好」时刻，重启后按这个时刻继续计算剩余时间。

### §3.5 phase 的用途

`phase` 字段是续跑判断的主依据。它必须能区分至少四种情形：

1. **没开始**：没有该 key 的任何记录；
2. **建好了**：已记录 `create` 且供应商侧确认存在新 key，但尚未完成推送（`created`）；
3. **推完了**：推送与回执已完成，尚未满足双活（`notified`）；
4. **双活等满了**：双活窗口已满足，可以停旧（`dwell`）。

仅凭「是否出现在某个已完成列表里」无法区分上述情形，因此 journal 记录里的 `phase`
必须被读出来并参与判定。

## §4 可观测性

- `resume()` 对无法解析的尾部残缺记录必须丢弃并给出可读的诊断，不得因为一条坏记录
  拒绝整份 journal。
- 对同一个 key 出现互相矛盾的记录（例如先 `revoked` 后又 `created`），按时间顺序取
  最后一个能自洽的状态，并把矛盾写进诊断。
