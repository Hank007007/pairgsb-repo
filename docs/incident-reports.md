# OTA 事故报告

本文件收录与 manifest 解析相关的已归档事故。报告只描述现象与影响范围，不给出
结论。

## INC-2417 两个 manifest 验签都通过，但解出的 targets 不同

**时间**：2024-11-08
**影响机型**：P1、P1-Pro、P20 各若干台
**严重度**：高

### 现象

运维在灰度批次中同时推送了两个 manifest：manifest A 与 manifest B 由同一个厂商私钥
签发，`key_id` 相同，内容在业务上被视为同一份升级。两者都通过设备验签。但设备
从 A 解析出的 `targets` 与从 B 解析出的 `targets` 在字段值上不一致，部分设备的
`url` 指向了不同的下载路径，部分设备的 `sha256` 与运维台账对不上。设备没有报错，
也没有产生任何告警。

### 复盘摘要

- 两份 manifest 的字段集合相同，语义相同。
- 两份 manifest 的字节串不同：服务端打包流水线里，A 由旧版工具生成、B 由新版
  工具生成，两者对同一份 map 的键写入顺序不同。
- 两份 manifest 都能通过设备的规范化校验。
- 事后对比：对同样的字段，两份 manifest 计算出的待签字节不一致；但验签在两端
  都返回成功。
- 同一台设备在两次 OTA 检查中分别收到 A、B 时，`targets` 选择结果会发生变化。

### 待查问题

1. 规范化校验是否覆盖了 map 中嵌套的结构？
2. 待签字节是如何得到的？它与 manifest 的键顺序、与 `sig`、`key_id` 两个字段
   之间是什么关系？
3. 验签通过是否能保证「两端看到的是同一份字段」？

## INC-2431 设备下载了一个 size 为负的分片

**时间**：2024-12-02
**影响机型**：P10
**严重度**：严重

### 现象

一台 P10 设备在 OTA 过程中下载器持续读取，流量耗尽后仍未停止，最终因存储写满进入
恢复模式。事后提取的日志显示，分片的 `size` 字段在下载器内部被记录为负数，下载器
将其解释为「长度无上限」，于是不断从连接读取直到失败。

### 复盘摘要

- 出问题的 manifest 由一台测试环境的签名服务生成，其分片 `size` 字段的原始值为
  `0xFFFFFFFFFFFFFFFF`，另有一次为 `0xFFFFFFFF`。
- manifest 通过了解析与验签，设备没有在任何阶段拒绝它。
- 同一 manifest 中另有一片的 `offset` 加 `size` 超过了 manifest 顶层声明的整包
  长度，设备同样没有察觉。
- 还有一次测试 manifest 中某个分片的 `sha256` 只有 16 字节，设备照样接受了该
  分片。
- 下载器对负数长度没有任何防御。

### 待查问题

1. manifest 的整数从 CBOR 到 Go 的转换过程中，超过有符号范围的取值会发生什么？
2. `size`、`offset` 与整包长度之间的约束是否被检查？
3. `sha256`、`url` 这类字段的长度和空值是否有约束？
4. 当同一机型在 `targets` 中重复出现时，解析器应该选择哪一个？

## INC-2455 设备选中了前缀相同但并非本机的分片（补充记录）

**时间**：2025-01-19
**影响机型**：P1
**严重度**：中

### 现象

P1 设备被推送了本应只发给 P10 与 P1-Pro 的固件。固件在 P1 上校验失败，设备反复
重试。

### 复盘摘要

- 该 manifest 中 `targets` 同时包含 `P1`、`P10`、`P1-Pro` 的条目。
- 设备上报的机型为 `P1`，但下载到的分片 `model` 为 `P10`。
- 排查发现设备侧的分片选择逻辑对机型做了前缀比较。
- 另有一份 manifest 中两个 target 的 `model` 都是 `P1`，设备没有报错，直接选中了
  其中一个。

### 查问题

1. 机型匹配是否要求完整相等？
2. 一份 manifest 中同一机型出现多次时，应当返回哪个 target？还是应当拒绝整份
   manifest？
