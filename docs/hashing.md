# Secret hashing

Normative specification for how token secrets are stored and compared.

## §1 Algorithm and parameters

Secrets are hashed with scrypt:

| parameter | value |
|---|---|
| `N` | 16384 |
| `r` | 8 |
| `p` | 1 |
| output length (`dklen`) | 32 bytes |
| salt length | 16 bytes |

The salt is generated by a cryptographically secure random source at hash
time. Parameters and salt are stored with the digest; they are not secret.
Operators may not lower the parameters, and verifiers use the parameters that
were stored with the record rather than assuming the current defaults.

## §2 Stored representation

The stored value is the ASCII string:

```
scrypt$<N>$<r>$<p>$<salt-hex>$<digest-hex>
```

All fields are present. `<salt-hex>` is exactly 32 lowercase hex characters
(16 bytes) and `<digest-hex>` is exactly 64 lowercase hex characters
(32 bytes). A record that does not parse against this shape is a storage
integrity error, never a successful match.

## §3 Comparison

Secret comparison is performed over the raw digest bytes using a
constant-time comparison primitive (for example `hmac.compare_digest` or
`secrets.compare_digest`).

* Comparing the hexadecimal strings with `==`, or comparing any other
  re-encoded form, is not acceptable.
* A comparison must not short-circuit on a length or prefix mismatch in a way
  that leaks how much of the input was correct.
* Verification derives the candidate digest from the presented secret using
  the stored salt and parameters, then compares full digests.

## §4 Multiple candidate records

A presented secret may need to be compared against more than one stored
record if identifiers are shared (see `docs/token-format.md` §5). Each
comparison follows §3 independently. A single matching record is sufficient
to authenticate the token; failing all candidates is an authentication
failure.

## §5 Handling of secrets

* The plaintext secret exists only in the return value of issuance (and in the
  caller's request during verification); it is never written to the database,
  and never written to logs or audit payloads.
* The stored hash and digest are also not copied into audit payloads.
* No secret or hash is included in error messages.
* Each issuance uses a fresh salt; no salt is reused across records.
