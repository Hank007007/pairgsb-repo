# 线上事故复盘

本文件收录与 condgrate 授权决策点相关的两起线上事故。复盘描述现象、时间线与影响，结论指向需要对照 `docs/policy-model.md` 复核的行为面。

---

## INC-2024-017 客户端自报 clearance 导致越权读取

**等级**：P1　**持续**：约 6 小时　**影响**：一个外部集成方读取了超出其合同范围的机密文档 42 份。

### 现象

集成方在调用内部文档 API 时，在请求体 `attributes.principal` 中附带 `"clearance": 9`。该主体在目录中的 clearance 为 2。网关把这些属性原样交给 PDP，PDP 判定 `principal.clearance >= 5` 成立，返回 permit。审计日志里该请求的命中策略与正常高密级员工完全一致，事中没有任何告警。

### 时间线

- 14:02　集成方上线新版本，开始在请求体携带完整主体属性快照。
- 14:05　首批越权读取成功，PDP 返回 permit。
- 16:40　数据 owner 发现某份 restricted 文档被外部账号访问，发起排查。
- 17:20　确认请求体属性与目录属性不一致。
- 20:10　集成方回滚，事故止血。

### 复盘结论

- PDP 对属性来源没有区分权威性：请求体中的值与目录同步的值被同等对待，同名时请求体的值生效。
- 条件求值时 `clearance` 的声明类型是 `number`，但参与比较的值没有被按声明类型统一转换，数值大小与字符串序混用，使越权值更容易绕过阈值。
- 缺少属性、类型对不上时求值结果被当作可放行，进一步放大了影响面。
- 需要对照 `docs/policy-model.md` §2、§3、§9、§10 复核：属性来源优先级、类型转换、缺属性的三值处理、以及 indeterminate 的最终结论。

## INC-2024-031 父级 deny 策略从未生效

**等级**：P1　**持续**：约 4 个月（自策略上线起）　**影响**：org 层一条面向承包商的全域 deny 从未拦截过任何请求。

### 现象

安全团队在 org 层挂了一条 deny：承包商的 `read` 一律拒绝，并附带 `notify-security` 审计要求。该 deny 上线后，project 层同时存在一条 permit。线上观察到的行为是：只要 project 层有任意命中策略，org 层的 deny 就不会出现在候选结论里。四个月里没有任何一次拒绝是由这条策略产生的，也没有任何调用方收到过它。

进一步排查还发现：

- target 中使用 `["*"]` 表示「覆盖整张类型表」的写法没有生效，org 层这条策略本身在多数请求上连 target 都没匹配上。
- 当 permit 与 deny 在同一层同时命中时，最终结论取决于候选的排列顺序，而不是 deny 优先。
- 即使最终结论是 deny，调用方仍然收到了来自 permit 的 obligation。

### 时间线

- 2024-03　org deny 随季度策略评审上线，评审记录标注「已覆盖全部承包商」。
- 2024-07　一名承包商通过 project 层 permit 读取了本应被 org deny 拦截的文档。
- 2024-07　复核策略链，确认 org deny 从未进入候选集合。

### 复盘结论

- 策略收集沿层级向上时，在遇到第一个有命中的层就停止，父层策略无法进入合并。
- target 的通配语义没有按分段通配实现，`"*"` 未被当作覆盖全部取值。
- 合并阶段没有坚持 deny 优先，也没有把 obligation 限定在 permit 结论上。
- 需要对照 `docs/policy-model.md` §5、§6、§7、§8 复核：target 通配范围、整条链的收集、deny 优先、obligation 传播条件。

## 共同教训

两起事故都不是单点失误：

1. **信任边界**：请求体是调用方输入，目录是权威来源，二者不能混同（INC-017）。
2. **求值必须三值**：「不知道」与「否」必须区分，缺属性、类型不符、表达式异常都要显式表达，并在最终结论上偏安全（INC-017）。
3. **层级与合并是安全属性**：收集不能因就近命中而截断，合并不能让顺序决定结论，deny 必须压过 permit（INC-031）。
4. **obligation 跟随结论**：只有 permit 才携带 obligation，deny 时不得下传（INC-031）。
