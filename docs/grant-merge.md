# scopejoin — 多凭证授权合并

scopejoin 计算「一个请求同时携带多张凭证时，最终有效的 scope 与角色是什么」。
网关把 OIDC access token、服务账号 credential、OAuth delegated token，以及可能
存在的匿名凭证一起交给 `internal/grant`，由它产出一份 `EffectiveGrant`。

本文件是**规范**：它规定正确行为应当是什么，不规定实现方式。

## §1 术语与凭证类型

| 类型常量 | 含义 | 是否有有效期 |
|---|---|---|
| `oidc_access_token` | IdP 签发的 OIDC access token，携带 `scope` | 有 |
| `service_account` | 内部服务签发的服务账号 credential，携带 `roles` | 有 |
| `delegated` | 由某个已持有凭证的发起人换取的受限 OAuth token | 有 |
| `anonymous` | 未认证或仅标记身份的凭证 | 无 |

「有效集」（effective grant）指经过合并、收窄、过滤之后，本次请求真正拥有的
scope 与角色集合。凭证在有效集中的出现与否，取决于 §7 的效期判断、§5 的
委托校验与 §6 的匿名规则。

## §2 输入与解析

- §2.1 每张凭证具有：类型、签发者、主体标识、scope 列表、角色条目列表、
  签发时间与过期时间。`oidc_access_token` 的 scope 既可能出现在空格分隔的
  `scope` 字符串中，也可能出现在 `scopes` 数组中，两者按出现顺序合并。
- §2.2 scope 在解析阶段保留原始写法；大小写归一属于集合运算阶段的事（§3.1）。
  空字符串 scope 丢弃。
- §2.3 角色条目由「名称 + 是否 deny」构成。名称为空的角色条目属于畸形输入，
  解析失败。
- §2.4 类型未知或载荷无法解析时返回错误，不允许静默降级为匿名凭证。
- §2.5 匿名凭证不通过普通解析流程创建，必须显式构造；其 scope 与角色恒为空。

## §3 Scope 集合运算

### §3.1 规范化

scope 比较前统一做两步：去掉首尾空白，转换为小写。规范形式（canonical form）
是小写形式；有效集中出现的 scope 一律为规范形式。因此 `Read` 与 `read` 是
同一个 scope。

### §3.2 多凭证合并取并集

同一请求内多张凭证的 scope 取**并集**，不是交集。任何一张有效凭证拥有的
scope 都进入候选集合；凭证之间的类型差异不改变这一点。并集结果按字典序排序。

### §3.3 互斥 scope

下列 scope 两两互斥，不允许同时出现在有效集中：

| 组 | 保留者 | 丢弃者 |
|---|---|---|
| 写入与只读 | `docs:write` | `docs:read` |
| 管理权限与只读身份 | `admin` | `readonly` |
| 持久会话与一次性会话 | `session:persistent` | `session:ephemeral` |

规则：一组内若同时出现两个成员，保留「保留者」列中的那一个，另一成员从有效集
中丢弃；仅出现一个成员时原样保留。该丢弃发生在规范化之后，因此大小写不同的
写法同样会被识别为一组冲突。互斥关系只作用于最终有效集，不改变单张凭证自身的
scope 列表。

### §3.4 特殊 scope：`offline_access`

`offline_access` 是授权管理类 scope，不是资源访问 scope，不能因为凭证合并而被
无限传播：

- 合并所用的有效凭证中，恰好有一张携带非空 scope，且该凭证是
  `oidc_access_token` 时，`offline_access` 保留；
- 其余任何情况（多张凭证、或唯一凭证不是 OIDC token）一律从有效集中丢弃；
- 丢弃与否不影响其他 scope 的保留。

## §4 角色合并

### §4.1 角色条目的比较

角色名称区分大小写，按原样比较；同一名称、同一 deny 状态的条目视为重复条目，
只保留一个。

### §4.2 deny 优先且不可被覆盖

同一角色的 deny 与 allow 同时存在时，合并结果必须是 **deny**。后加入的 allow
条目不能把先前出现的 deny 冲掉；合并顺序不影响结果。deny 是限制，只能收紧，
不能被任何凭证的 allow 放宽。

### §4.3 输出

合并后的角色按名称字典序排序输出，每个名称至多一条。

## §5 委托链收窄

委托凭证（`delegated`）只能持有发起人自己已经拥有的权限，这是防止提权的核心
约束。发起人由委托凭证中的发起人主体标识确定，与有效集中的某张凭证主体匹配。

### §5.1 scope 不得超出

delegated 凭证的每个 scope（按 §3.1 规范化后比较）都必须包含在发起人的 scope
集合中。收窄后的 delegated scope 为二者交集。

### §5.2 角色不得超出

delegated 凭证中每个 allow 角色都必须由发起人显式持有；发起人没有的角色、
或发起人仅有 deny 的角色，都视为超出授权。delegated 凭证中的 deny 条目属于
收紧，不需要发起人持有，予以保留。

### §5.3 整份拒绝

只要 delegated 凭证的 scope 或角色有任何一项超出 §5.1、§5.2 的约束，**整份
delegated 凭证拒绝**：它不贡献任何 scope，也不贡献任何角色，而不是只丢弃
越权的那一项。其他凭证不受影响，请求照常计算。委托链可以不止一层，每一层都
必须逐层满足 §5.1 与 §5.2；发起人缺失或链成环时，该 delegated 凭证同样被拒绝。

## §6 匿名凭证

匿名凭证不贡献 scope，也不贡献角色，不参与委托链的发起人匹配，不使计算失败。
若请求中只有匿名凭证，有效集为空。匿名凭证也不计入 §3.4 的凭证张数。

## §7 有效期与时钟偏移

### §7.1 按来源区分的偏移额度

判定凭证是否有效时，除过期时间外还要容忍网关与签发方之间的时钟偏移。容忍额度
按凭证来源（类型）区分：

| 来源类型 | 容忍额度 |
|---|---|
| `oidc_access_token` | 120 秒 |
| `delegated` | 60 秒 |
| `service_account` | 30 秒 |
| `anonymous` | 0（匿名凭证无有效期） |

不得对所有来源使用同一个固定值。

### §7.2 边界口径

设凭证过期时间为 `exp`，该来源的容忍额度为 `skew`，当前时间为 `now`。凭证在

```
now <= exp + skew
```

时视为有效；仅当 `now` 严格晚于 `exp + skew` 时才过期。也就是说，恰好等于
`exp + skew` 的那一刻仍然有效。过时间缺省（零值）表示该凭证不失效。

## §8 输出

`EffectiveGrant` 包含有效主体标识、有效 scope（规范形式、字典序）与有效角色
（字典序）。scope 与角色的输出顺序是稳定的，便于比较与展示。主体标识取第一张
进入有效集的非委托凭证的主体；没有时取第一张通过 §5 校验的委托凭证的主体；
都没有（例如只有匿名凭证）时为空字符串。
