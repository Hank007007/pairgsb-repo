# design — filtergate-doc-query

本文件说明网关的分层职责与各部分「正确的行为」，作为实现与评审的共同参照。
语法细节以 [`filter-grammar.md`](filter-grammar.md) 为准。

## 1. 目标

前端需要一种受限的查询语言来检索日志，又不能把后端查询能力直接暴露出去。
网关位于两者之间，把一段 JSON filter 收敛成一个明确、可审计的后端查询文档。

三个不可让步的目标：

1. **只放行规范内的东西。** 允许的算子、字段、结构由规范正向定义，其余一律拒绝。
2. **租户边界由网关持有。** 租户值来自登录态，客户端输入无法参与决定。
3. **失败快、失败早。** 所有拒绝都发生在 `compile()` 内，后端 adapter 不参与校验。

## 2. 分层

```
调用方 ── filter JSON ──▶ FilterGate.compile(filter, tenant_id)
                              │
                              ├─ 1. 结构校验
                              ├─ 2. 算子白名单
                              ├─ 3. 字段白名单
                              ├─ 4. 资源上限（深度 / 数组长度 / pattern 长度）
                              ├─ 5. 类型校验与规范化
                              ├─ 6. 租户作用域注入
                              └─ 7. adapter.to_backend(node, tenant_id)
                                        │
                                        ▼
                                   后端查询文档
```

**第 1–6 步全部属于网关。** adapter 只做翻译：它接收已经合法、已经规范化的
节点树，不重复校验，也不承担拒绝非法输入的职责。把校验下沉到 adapter 会让
其他 adapter 各自实现一遍，且无法保证「拒绝时 adapter 未被调用」。

## 3. 各层职责

### 3.1 结构层

把 filter 解析成统一的节点树：

- 逻辑节点：`and` / `or`，挂若干子节点；
- 字段节点：字段名 + 若干算子子句。

解析阶段同时完成「形态」判断：根必须是对象、字段值必须对象、逻辑算子操作数
必须是非空数组、字段值对象不能为空。形态不对与「不认识的算子」是两类不同错误，
前者 `INVALID_FILTER`，后者 `UNKNOWN_OPERATOR`。

### 3.2 算子层

允许集合是**正向列举**的：逻辑算子两个，比较算子六个，加上 `$in`、`$regex`
及其修饰符 `$options`。任何不在此集合中的 `$` 开头 key 都必须被拒绝——无论它
出现在节点层还是字段值层。规范 §5.4 列出的禁用算子（`$where`、`$expr`、
`$function`、`$accumulator` 等）只是这一规则的显式例子，不是全部。

判断「是否允许」只应针对算子名本身，不应根据它出现在哪一层而放宽。

### 3.3 字段层

字段必须与白名单全名匹配。字段名中的 `.` 会被存储层解释为路径分隔符，因此
含 `.` 的字段名必须被当作非法字段拒绝，而不能被拆成「顶层字段 + 子路径」放行。
含 `$` 的字段名同样拒绝。

### 3.4 资源层

深度与长度都在解析阶段判定：

- 深度在进入子节点之前检查，根记为 1，超过上限即返回 `DEPTH_EXCEEDED`。
  超深输入必须得到确定的错误码，而不是让解释器栈溢出。
- `$in` 数组长度、`$regex` pattern 长度同理，超限分别返回 `LIST_TOO_LONG` 与
  `REGEX_INVALID`。

### 3.5 类型层

每个字段有且仅有一个声明类型。操作数必须与声明类型一致：

- 不做字符串/数字之间的隐式转换；
- 布尔值不视为整数；
- `$in` 必须是数组，且每个元素都与字段类型一致；
- 类型不符统一返回 `TYPE_MISMATCH`。

类型规范化只发生在确认类型一致之后，目的是让下游拿到确定的 Python 类型，
而不是借此接受原本不合法的输入。

### 3.6 租户层

租户条件由网关构造，并作为查询根 `and` 的一部分注入。用户 filter 中出现的
`tenant_id` 条件不参与最终结果：网关要么整体丢弃它，要么保证它在任何情况下都
不能替换、追加或削弱注入的条件。

关键不变量：**最终查询中的租户值恒等于会话租户**。这应当由结构保证，而不是
依赖合并顺序的偶然结果。

### 3.7 翻译层

adapter 把节点树映射为 §9 规定的查询结构：

- 同层 `and` 展平；
- 子句按规范化序列化排序，保证相同语义得到相同查询；
- `$regex` 按字面量语义处理，pattern 在下发前转义，`$options` 只携带网关确认过的
  字符集合。

## 4. 失败语义

- `compile()` 只有两种结局：返回成功结果，或返回带定错误码的失败结果。
  非法输入不应以异常形式逃逸到调用方。
- 失败时 adapter 的调用次数必须为 0。
- 错误码在 `ErrorCode` 中定义，只允许新增。

## 5. 可验证的行为

以下行为应能通过真实调用观察到：

1. 禁用算子（`$where` / `$expr` / `$function` / `$accumulator` / `$text` /
   `$jsonSchema`）在 `compile()` 返回 `UNKNOWN_OPERATOR`，adapter 未被调用。
2. 带 `tenant_id` 的 filter 编译后，租户子句的值等于会话租户。
3. 深度 5000 的 `$and` 返回 `DEPTH_EXCEEDED`；长度 5000 的 `$in` 返回
   `LIST_TOO_LONG`。
4. 字段名含 `.` 返回 `FIELD_NOT_ALLOWED`；`$options` 含 `i`/`m` 之外字符返回
   `REGEX_INVALID`。
5. `$in` 传非数组、整数字段传数字字符串返回 `TYPE_MISMATCH`。
6. 正常 filter 的翻译结果与 `tests/snapshots/demo_query.json` 逐字段一致。

## 6. 非目标

- 不实现查询执行引擎；adapter 的 `execute()` 只是占位。
- 不引入第三方依赖。
- 不改变 `compile()` 的签名与返回类型。
