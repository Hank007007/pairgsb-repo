# keycustody 阈值密钥托管设计说明

状态：规范性文档（Normative）
适用范围：本文描述 keycustody 对外可观察的行为约，不描述具体实现方式。

## §1 术语与组件

- **主密钥（master key）**：被托管的秘密字节串，恢复流程的唯一合法输出。
- **分片（shard）**：主密钥经门限切分后交给单个托管方保存的数据单元。
- **托管批次（split）**：一次完整的门限切分所产生的全部分片，由 `split-id` 标识。
- **generation**：同一份主密钥可以经历多次重新切分；`generation` 标识分片所属的那一次切分。`split-id` 与 `generation` 共同确定批次身份。
- **custody-id**：主密钥所属租户/托管域的标识，是分片归属的唯一依据。
- **approver-id**：审批主体的稳定标识，同一主体的所有提交共享该标识。
- **role**：审批主体在组织中的角色，按 §6 的层级结构解释。
- **gate**：审批门限判定。
- **policy**：角色到 allow/deny 的规则集合。
- **flow**：把审批、取片、合并、完整性校验串起来的恢复编排。

组件边界：

| 组件 | 职责 |
|---|---|
| 切分与合并 | 生成分片、从分片重建主密钥 |
| 审批 | 门限判定与角色策略判定 |
| 分片存储 | 按 custody-id 保存与读取加密分片 |
| 恢复编排 | 串联审批、读取、合并、校验与敏感数据清理 |

## §2 分片身份与批次绑定

1. 每个分片必须携带：`shard-id`、`split-id`、`generation`、`index`、`threshold` 以及分片数据。
2. 同一次切分产生的所有分片，其 `split-id` 与 `generation` 必须完全一致。
3. 合并操作的输入必须来自同一个 `split-id` 且同一个 `generation`。
4. 输入中只要存在任何一个分片的 `split-id` 或 `generation` 与其他分片不同，合并必须失败并返回错误。
5. 合并失败时不得返回任何候选主密钥，也不得把部分合并结果交给调用方。
6. `split-id` 为空或 `generation` 为负数的分片不构成合法输入。

## §3 切分

1. 切分参数包括：主密钥、分片总数 N、门限 M、`split-id`、`generation`。
2. 约束：主密钥非空；`1 <= M <= N <= 255`；`split-id` 非空；`generation >= 0`。
3. 任意少于 M 个分片的组合不得恢复出主密钥；任意不少于 M 个且 index 互不相同的同批次分片必须能恢复出主密钥。
4. 分片数据长度必须等于主密钥长度。
5. 每次切分必须使用独立的随机材料，不得复用上一次切分的随机性。

## §4 重建

1. 合并至少需要 `threshold` 个分片；不足时返回错误。
2. 输入中出现重复的 `index` 时返回错误，不得静默去重或抵消。
3. 输入的分数据长度不一致，或 `index` 超出 `1..255` 时返回错误。
4. 只有在 §2 的批次一致性校验通过后，才允许进行重建计算。
5. 重建结果在通过调用方提供的完整性摘要校验之前，不得作为成功结果返回。
6. 合并返回的错误不得包含分片数据内容。

## §5 审批门限

1. 审批门限按**去重后的审批主体数**计算，而不是按提交条数计算。
2. 每个审批主体以 `approver-id` 唯一标识；同一 `approver-id` 在一次审批中无论提交多少次，最多只计一票。
3. 只有 `approve` 票计入通过票数；`reject` 票具有一票否决效果。
4. 去重后的 `approve` 主体数达到 `required` 且不存在任何 `reject` 时，门限才算通过。
5. 未通过门限时，恢复流程不得读取或解封任何分片。
6. `approver-id` 为空的提交不计为有效主体。

## §6 审批策略

### §6.1 角色层级

角色按如下树形结构解释，箭头方向为“子角色 -> 父角色”：

```
admin
├── ops
│   └── ops-oncall
└── auditor
    └── ops-readonly
```

即：`ops-oncall` 的父角色是 `ops`；`ops` 与 `auditor` 的父角色是 `admin`；`ops-readonly` 的父角色是 `auditor`。`ops` 与 `ops-readonly` 之间不存在父子关系。

### §6.2 匹配规则

1. 一条角色为 R 的策略规则适用于请求角色 X，当且仅当 `X == R`，或 R 是 X 的祖先角色（沿 §6.1 的父角色链向上可达）。
2. 匹配必须按角色层级进行，不得按字符串前缀、后缀或包含关系进行。
3. 因此，`ops` 的规则不适用于 `ops-readonly`；`admin` 的规则适用于全部四种角色。

### §6.3 求值规则

1. 求值时必须收集**所有**匹配的规则，而不是遇到第一条匹配就结束。
2. 只要存在任意一条匹配的 `deny` 规则，最终结果就是 deny。
3. 否则，只要存在任意一条匹配的 `allow` 规则，最终结果就是 allow。
4. 否则结果为“无匹配”，调用方按默认拒绝处理。
5. 最终结果与规则在策略集合中的排列顺序无关。

## §7 租户隔离

1. 写入分片时必须记录该分片归属的 `custody-id`。
2. 读取分片的接口必须同时接收请求方的 `custody-id` 与目标 `shard-id`。
3. 读取时必须核对分片记录的归属 `custody-id` 与请求方 `custody-id`；二者不一致时返回错误，并且不得返回任何分片数据或元数据。
4. 租户隔离校验必须先于解密与返回。
5. `shard-id` 不是全局可读句柄；知道其他租户的 `shard-id` 不构成读取权限。
6. 读取不存在的分片与读取越权分片都必须以错误结束。

## §8 恢复编排与敏感数据生命周期

1. 恢复顺序为：审批门限判定 → 读取并解封分片 → 批次一致性校验与合并 → 完整性摘要校验 → 返回主密钥。
2. 解封后的明文分片只能存在于恢复流程专用的临时缓冲区中，不得写入长期存储。
3. 无论恢复成功还是失败，流程退出前都必须将临时缓冲区中的明文分片清零，并释放其引用。
4. 失败路径同样适用上一条；错误返回不得绕开清理。
5. 日志（任何级别，包括 debug）与错误信息中不得出现分片数据内容，也不得出现其十六进制、Base64 等可还原编码。
6. 日志可以记录 `shard-id`、`custody-id`、数量、错误类别等元数据，但不得记录分片字节。
7. 完整性摘要不匹配时必须返回错误，且不得返回重建出的主密钥。
8. 流程返回的错误应携带足够的定位信息（如分片标识、失败阶段），但不得携带秘密材料。

## §9 静态存储

1. 分片在存储中必须加密保存；加密密钥不与被托管的分片放在同一位置。
2. 加密必须提供完整性保护；被篡改的分片在读取时必须解密失败。
3. 同一分片重复写入时，以最后一次写入为准，但仍需保留其 `custody-id` 归属。

## §10 可观察行为

1. 对调用方而言，错误必须通过返回值表达，不得以“返回零值主密钥”代替错误。
2. 任何违反 §2、§4、§5、§6、§7、§8 的输入都必须产生可检测的错误。
3. 命令行入口只用于演示完整流程，不改变上述各包的约束。
