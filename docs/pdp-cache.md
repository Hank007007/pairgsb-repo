# PDP 决策缓存设计说明

permcache 是策略决策点（PDP）中的决策缓存中间层。上游是策略 bundle，下游是授权请求。
本文规定该系统**必须**表现出的行为语义，是实现、评审与测试的共同依据。

文中「必须」「不得」表示强制要求；「应」表示除非有充分理由否则应当遵守。

## 1. 概述

一次授权请求由租户、主体、动作、资源以及一组请求属性构成。系统在策略规则上求值，
得到 allow 或 deny 的决策。由于请求量远大于策略变更频率，求值结果按请求维度缓存；
策略 bundle 更新后，旧决策不得继续被命中。

## 2. 数据模型

### 2.1 Bundle

一个 bundle 是一份完整、不可变的规则集合：

| 字段 | 含义 |
|---|---|
| `Revision` | 非负十进制整数，以字符串编码，表示 bundle 的版本 |
| `Rules` | 规则列表 |

同一时刻只有一个 bundle 处于生效状态（见 §7）。bundle 内的规则 ID 必须唯一。

### 2.2 Rule

| 字段 | 含义 |
|---|---|
| `ID` | 规则标识，bundle 内唯一 |
| `Effect` | `allow` 或 `deny` |
| `Tenant` | 规则所属租户；`*` 表示适用于所有租户 |
| `Subject` | 主体模式（§10.1） |
| `Action` | 动作模式（§10.2） |
| `Resource` | 资源模式（§10.1） |
| `NotBefore` | 生效起点，零值表示无下界 |
| `NotAfter` | 生效终点，零值表示无上界；区间为左闭右开 |

### 2.3 请求与决策

请求：`Tenant`、`Subject`、`Action`、`Resource`、`Attributes`（字符串键值对）。

决策：`Effect`、`MatchedRule`（决定该结果的规则 ID，默认决策为空）、`Revision`
（产生该决策时的策略 revision）、`Cached`（本次结果是否来自缓存）。

## 3. 缓存键

### 3.1 组成

缓存键必须完整覆盖请求的决策相关维度，由以下六部分构成：

1. 租户 `tenant`
2. 主体 `subject`
3. 动作 `action`
4. 资源 `resource`
5. 请求属性指纹（§3.2）
6. 策略 `revision`

任意两个请求只要在上述任一部分不同，就必须得到不同的键。特别地：

- 同一主体对 `read` 与 `delete` 是两个不同的缓存维度，不得互相命中；
- 同一主体、动作、资源在不同租户下是不同维度，不得互相命中。

各组成部分之间必须使用无歧义的分隔或转义，避免例如
`subject="a|b"` 与 `subject="a", resource="b"` 拼出相同字符串。

### 3.2 属性指纹

`Attributes` 是无序映射，其指纹必须只由集合的内容决定，而不是由遍历顺序、插入顺序或调用
次数决定。具体要求：

- 同一个属性集合在任意次数、任意进程中的指纹逐字节相同；
- 两个不同的属性集合（键不同，或同名键的值不同）必须得到不同指纹；
- 指纹不得因某个属性名或值中包含分隔字符而与另一个集合混淆；
- 空映射与 `nil` 必须得到相同的指纹。

### 3.3 稳定性

对同一请求（相同字段、相同属性集合）反复调用，缓存键必须逐字节相同，与 map 的遍历
顺序、插入顺序、调用次数无关。键的稳定性直接决定命中率。

### 3.4 revision 参与键

`revision` 必须进入缓存键。策略更新后 revision 改变，旧 revision 下写入的条目不得再被
任何请求命中（见 §7.3）。

## 4. 租户隔离

- `tenant` 是缓存键的一部分，不同租户的缓存互不可见。
- 规则匹配时，`Rule.Tenant` 为 `*` 或等于请求租户，规则才可能命中。
- 规则中的 `*` 租户只表示「规则适用于所有租户」，不表示不同租户可以共享缓存条目。
- 撤销、统计等操作也必须以租户为边界（§8）。

## 5. 生效区间与缓存有效期

- 规则生效判定：`NotBefore <= now < NotAfter`；两端为零值时对应方向无界。
- 不在生效区间内的规则不得参与匹配，视同不存在。
- 缓存条目必须携带过期时间。过期时间不得晚于 `now + TTL`，并且不得晚于当前 bundle
  中任一条规则的生效区间边界；这样规则进入或退出生效区间时，缓存不会继续返回旧结论。
- 读取时已过期的条目视为 miss，并应从存储中移除。

## 6. 求值语义

### 6.1 匹配

一条规则命中请求，当且仅当以下条件同时成立：

1. 租户匹配（§4）；
2. 主体匹配（§10.1）；
3. 动作匹配（§10.2）；
4. 资源匹配（§10.1）；
5. 规则在生效区间内（§5）。

### 6.2 deny 优先

在所有命中的规则中，只要存在 `deny`，最终决策必须为 `deny`。该优先级与规则在 bundle
中的顺序无关，也与决策是否来自缓存无关。

### 6.3 默认决策

没有任何规则命中时，最终决策为 `allow`，`MatchedRule` 为空。

## 7. revision 与热更新

### 7.1 编码

revision 是不带符号的十进制整数字符串，不得假设固定宽度，位数可以任意长。
前导零可以接受，但数值相等即视为同 revision。

### 7.2 比较

revision 必须按**数值**比较，而不是按字符串字典序：

- `"9"` 小于 `"10"`；
- `"100"` 大于 `"99"`；
- `"010"` 与 `"10"` 相等。

比较结果必须与 revision 的位数无关。

### 7.3 热更新

加载新 bundle 时：

- 新 revision 小于当前 revision：拒绝加载，返回可识别的「过期 revision」错误；
- 新 revision 等于当前 revision：幂等替换；
- 新 revision 大于当前 revision：立即生效。

新 bundle 生效后，先前 revision 下写入的缓存条目必须立刻不可命中。已存在的旧条目可以
保留到自然过期，但不得被读取为有效决策。

## 8. 撤销

撤销消息描述一个作用域：

| 字段 | 含义 |
|---|---|
| `Tenant` | 租户；`*` 表示所有租户 |
| `Subject` | 主体；`*` 表示所有主体，否则精确匹配 |
| `Action` | 动作模式；`*` 表示所有动作 |
| `Resource` | 资源模式；`*` 表示所有资源 |

撤销必须删除作用域内的**全部**缓存条目，不论：

- 条目的 action 是具体值还是来自通配规则；
- 条目的租户是具体值还是来自通配租户规则；
- 条目写入时的 revision；
- 条目当初是通过通配 action 或通配租户的则产生的。

也就是说，`*` 必须在撤销时展开为「匹配任意值」，不能按字面字符串比较。撤销应返回实际
删除的条目数量。四个字段均不得为空。

例：`{Tenant: "*", Subject: "user:alice", Action: "*", Resource: "*"}` 必须清空
`user:alice` 在所有租户下的全部缓存决策；下一次请求必须重新求值。

## 9. 命中与 miss

- **命中**：按 §3 构造键并找到未过期条目。直接返回条目中的决策，`Cached=true`，
  不得重新求值，命中计数加一。
- **miss**：未找到条目或条目已过期。重新求值，按 §5 写入缓存，`Cached=false`，
  miss 计数加一。
- 命中路径返回的决策内容必须与写入时一致：写入时是 deny，命中时仍是 deny。
- 引擎必须提供命中、miss、撤销删除数量的累计统计，供运行期观察。
- 统计计数只增不减，并且并发安全。

## 10. 模式匹配

### 10.1 subject 与 resource

模式中的 `*` 匹配任意长度（含零）的字符序列，可以跨越 `:`、`.`、`/` 等字符；其余字符
按字面比较。例如 `user:*` 匹配 `user:alice` 与 `user:team:core`。

### 10.2 action

action 是以 `.` 连接的多段标识（如 `read`、`docs.read`、`docs.read.private`）。

- 模式中的 `*` 匹配任意长度（含零）的字符序列，包括 `.` 本身；
- `docs.*` 必须匹配 `docs.read`、`docs.read.private` 与 `docs.` 后的任意动作；
- 单独的 `*` 必须匹配所有 action，包括多段 action；
- 非通配段按字面逐段比较。

因此 `docs.*` 是 `docs` 名称空间下所有动作的前缀模式，而不是「`docs` 加恰好一段」。

## 11. 可观测性与并发

- 缓存存储与决策引擎必须可被多个 goroutine 并发调用；内部状态不得数据竞争。
- 键构造是纯函数，不依赖全局状态。
- 命中、miss、失效计数在进程生命周期内单调递增。
- 规则与 bundle 对外暴露时不得被调用方就地修改而影响后续决策。
